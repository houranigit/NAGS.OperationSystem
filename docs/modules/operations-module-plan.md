# Operations implementation scope

Read [Operations Module Foundation](operations-foundation.md) for the current behavior and ownership. This branch implements the flight scheduling baseline from `main`; it does not inherit the separate HandOver implementation.

The current scope is the flight register, single/batch scheduling, basic planning edits, direct planned-service and staff lists, add-only employee invitations, existing authorization, and optimistic concurrency. Android shares the online flight-list/details/invitation API journey; flight creation and single/batch scheduling stay in the web portal. Shared MasterData catalog caching/synchronization remains available independently, using its existing lookup permissions and a separate cache keyed by API environment and account. The restored Sync Center displays connectivity, live catalog-channel status, per-catalog freshness/count/duration/errors, and manual refresh; it does not restore WO or offline flight workflows. Work orders, actual work, history, status changes, handover, review, reports, and offline Operations workflows will be considered individually in later work; this document does not authorize their implementation.

Verify this baseline with the solution build, retained flight domain/application checks, portal checks, SQL endpoint authorization/concurrency tests, invitation/notification checks, and a SQL migration test covering preservation of flight planning data and retained invitation envelopes. Android verification covers API paging/details/invitation calls, permission and stale-version behavior, catalog payload/access/cache-refresh behavior and live mutation invalidation, unit checks, lint, and debug assembly; observed emulator journeys are reported separately. Record actual verification results in the change report rather than carrying forward results from retired features.
