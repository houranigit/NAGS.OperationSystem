# Operations implementation scope

Read [Operations Module Foundation](operations-foundation.md) for the current behavior and ownership. This branch retains the flight scheduling baseline from `main` and adds arrival, departure, and cancellation submissions, performed flight services, flight tasks, and return-to-ramp occurrences at the domain and persistence boundary, plus the arrival API/Android save workflow documented in the foundation; it does not inherit the separate HandOver implementation.

The current scope is the flight register, single/batch scheduling, basic planning edits, direct planned-service and staff lists, add-only employee invitations, existing authorization, optimistic concurrency, and authenticated arrival saving. Android shares the scoped flight-list/details API with read-only caching, on-open detail persistence, a Flights Sync Center card, and flight-only live refresh hints; invitations remain online; flight creation and single/batch scheduling stay in the web portal. Shared MasterData catalog caching/synchronization remains available independently, using its existing lookup permissions and a separate cache keyed by API environment and account. The restored Sync Center displays connectivity, live catalog-channel status, per-catalog and flight freshness/count/duration/errors, and manual refresh; it does not restore WO or the legacy offline uploader. The independent arrival queue is the sole offline flight-write workflow in this step. Other actual work, work orders, history, status changes, handover, approval review, reports, and further offline Operations workflows will be considered individually in later work; this document does not authorize their implementation.

The domain and persistence slices implement the [arrival](operations-foundation.md#arrival-submissions), [departure](operations-foundation.md#departure-submissions), [cancellation submission](operations-foundation.md#cancellation-submissions), [performed-service](operations-foundation.md#flight-services), [task](operations-foundation.md#flight-tasks), and [return-to-ramp rules](operations-foundation.md#return-to-ramp), with the shared [persistence boundary](operations-foundation.md#operational-persistence-boundary). Normal and RTR departures share the five-field `CustomerSignature` metadata value (`FileName`, `StorageKey`, `ContentType`, `SizeBytes`, `SignedAtUtc`), with the same validation and independent copied instances. It is required for normal departure and optional for RTR departure. Signatures and attachments store metadata for later integration with the existing file-storage boundary. Additive Operations migrations are not applied to configured databases. The normal-departure legacy signature fallback and preflight policy are documented under [database changes](operations-foundation.md#database-change); existing RTR signature metadata is preserved. Beyond arrival saving, operational endpoints, application screens, offline writes, file transfers, approval selection, reopening, return-to-ramp application workflows, task application workflows, pricing, stock consumption, billing, and further lifecycle policies remain outside these slices. The accepted `main` service/resource business rules remain the baseline: retain typed Quantity/Duration usage and snapshot calculation types, numeric limits, unique selections, parent-bound periods, Unknown-selection notes/text limits, and typed attachment limits. Direct flight ownership, open windows, stable child corrections, and task/performer notes are the agreed model changes; application validation and completion workflows remain phased work.

Verify submissions, performed services, tasks, and return-to-ramp occurrences with focused domain checks for required and optional fields, file metadata, open and invalid time windows, stable scoped corrections and no-ops, acceptance transitions, Major/Minor task types, optional ATA chapters, resource and employee notes, repeated service occurrences, quantity/duration branches and precision, calculation-type agreement, resource/employee uniqueness and containment, Unknown-selection notes and length limits, attachment kind/count/metadata limits, start/end actor attribution, any-departure and single-open-occurrence gates, stable occurrence numbers, arrival/departure corrections, shared signature metadata/validation, required normal and optional RTR signatures, independent signature ownership, occurrence completion/bounds, cancellation exclusivity including unaccepted submissions, and preservation of planning data. Persistence checks cover round trips, per-flight submitter and per-parent selection uniqueness, quantity/duration SQL check constraints, nested service/task/occurrence changes and removals under concurrency, single-open and sequence indexes, composite occurrence ownership, and preservation of existing flight and operational data. Mutation loads use mapped `ServiceRecords`/`TaskRecords` plus the occurrence graph; public `Services`/`Tasks` continue to expose normal work only.

Verify this baseline with the solution build, retained flight domain/application checks, portal checks, SQL endpoint authorization/concurrency tests, invitation/notification checks, and a SQL migration test covering preservation of flight planning data and retained invitation envelopes. Android verification covers API paging/details/invitation calls, permission and stale-version behavior, catalog payload/access/cache-refresh behavior and live mutation invalidation, unit checks, lint, and debug assembly; observed emulator journeys are reported separately. Record actual verification results in the change report rather than carrying forward results from retired features.
