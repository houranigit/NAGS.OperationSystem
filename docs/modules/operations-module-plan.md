# Operations implementation scope

Read [Operations Module Foundation](operations-foundation.md) for the current behavior and ownership. This branch retains the flight scheduling baseline from `main` and adds arrival, departure, and cancellation submissions and performed flight services at the domain and persistence boundary; it does not inherit the separate HandOver implementation.

The current scope is the flight register, single/batch scheduling, basic planning edits, direct planned-service and staff lists, add-only employee invitations, existing authorization, and optimistic concurrency. Android shares the scoped flight-list/details API with read-only caching, on-open detail persistence, a Flights Sync Center card, and flight-only live refresh hints; invitations remain online; flight creation and single/batch scheduling stay in the web portal. Shared MasterData catalog caching/synchronization remains available independently, using its existing lookup permissions and a separate cache keyed by API environment and account. The restored Sync Center displays connectivity, live catalog-channel status, per-catalog and flight freshness/count/duration/errors, and manual refresh; it does not restore WO or offline flight mutations. Other actual work, work orders, history, status changes, handover, review, reports, and offline Operations workflows will be considered individually in later work; this document does not authorize their implementation.

The domain and persistence slices implement the [arrival](operations-foundation.md#arrival-submissions), [departure](operations-foundation.md#departure-submissions), [cancellation submission](operations-foundation.md#cancellation-submissions), and [performed-service rules](operations-foundation.md#flight-services), with the shared [persistence boundary](operations-foundation.md#operational-persistence-boundary). Signatures and attachments store metadata for later integration with the existing file-storage boundary. Additive Operations migrations are not applied to configured databases. Operational endpoints, application screens, offline writes, file transfers, approval selection, reopening, RTR, tasks, billing, and further lifecycle or chronology policies remain outside these slices.

Verify submissions and performed services with focused domain checks for required and optional fields, file metadata, open and invalid time windows, stable scoped corrections and no-ops, acceptance transitions, repeated services and employee periods, cancellation exclusivity including unaccepted submissions, and preservation of planning data. Persistence checks cover round trips, per-flight submitter uniqueness, nested service changes and removals under concurrency, and preservation of existing flight and operational data.

Verify this baseline with the solution build, retained flight domain/application checks, portal checks, SQL endpoint authorization/concurrency tests, invitation/notification checks, and a SQL migration test covering preservation of flight planning data and retained invitation envelopes. Android verification covers API paging/details/invitation calls, permission and stale-version behavior, catalog payload/access/cache-refresh behavior and live mutation invalidation, unit checks, lint, and debug assembly; observed emulator journeys are reported separately. Record actual verification results in the change report rather than carrying forward results from retired features.
