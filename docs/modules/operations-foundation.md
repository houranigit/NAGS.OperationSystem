# Operations Module Foundation

This is the entry point for the current Operations module. This branch starts from `main` with a flight scheduling baseline: maintain a flight register, create one flight, schedule the same flight on selected dates, and invite employees onto an existing flight. Arrival has an API and local-first Android save workflow. Departure has a save API with customer-signature storage and a local-first Android save workflow. Cancellation has save/revert APIs and a local-first Android workflow. Performed flight services, flight tasks, and return-to-ramp occurrences remain domain and persistence models. The Android client supports flight viewing, details, arrival/departure saving, cancellation saving/reversion, and employee invitations; scheduling remains in the web portal. HandOver implementation is excluded. Further operational APIs and application workflows will be designed and implemented individually later.

## Flight data and ownership

`Flight` owns customer, station, operation type, flight number, scheduled arrival/departure, optional aircraft type, planned services, assigned employees, operational submissions, performed services, tasks, and return-to-ramp occurrences. MasterData remains authoritative for reference records; Operations validates selections through its existing readers and stores snapshots. Planned services and assigned employees are direct flight collections.

Creation/update timestamps, creator ID, and SQL rowversion support persistence and concurrency. Android derives its display-only progress badge from existing submissions and the current account’s durable local queues. The labels cover Draft, submitted arrival/departure/cancellation, pending synchronization, cancellation reversion awaiting sync, and needs review. Local cancellation intent takes precedence; a queued work correction remains visibly pending. The badge adds no stored status or approval state. There is one current scheduled flight number. Beyond the submission, performed-service, task, and return-to-ramp models described below, a stored flight status, original-number history, contract placeholders, merge metadata, other actual work, work orders, handover, review, approval, timeline, file transfers, and automatic work creation remain outside this scope. Platform audit capture remains enabled independently of a flight history feature.

## Arrival submissions

`Flight.ArrivalSubmissions` owns `FlightArrivalSubmission` entities, each containing an `ArrivalDetails` value object. ATA, actual aircraft type, aircraft tail number, and the receiving employee are required. Customer work reference number and remarks are optional; whitespace-only optional values become null. ATA is stored in UTC and is not constrained by the scheduled arrival or departure. Actual aircraft details do not replace the flight's planned aircraft type.

Each submitting `StaffMemberId` has at most one arrival submission per flight. Updating that employee's submission preserves its identity; the receiving employee can differ from the submitter. A sole submission is accepted automatically. Adding a second employee's submission clears acceptance, and submissions remain unaccepted while multiple records exist. Selecting an accepted record belongs to a later approval workflow.

### Arrival save workflow

Open Flight opens the existing flight form. Its top-right Save retains durable arrival and departure input on the device through the separate queues described below. Services and tasks remain later steps; cancellation uses its separate workflow below. The initial submission and receiving employee are both attributed server-side to the authenticated linked staff member. ATA, actual aircraft type, and tail number are required; reference and remarks remain optional. Validation follows the existing arrival model without adding schedule bounds or arbitrary text limits. Android also requires a current eight-byte rowversion and an aircraft from its cached active catalog; the server rechecks catalog eligibility and mobile flight access.

`PUT /api/v1/operations/flights/{id}/arrival` requires `operations.flights.operate` and `If-Match`, with the same active staff/station, membership/category, and rolling-window boundary as mobile details. Missing/invalid preconditions and invalid fields use the existing validation response (`400`); stale changes return `409`. The response contains the saved arrival and current flight rowversion. An identical retry of the caller's existing input acknowledges the saved record without another write, even with the original version, so a lost success response can be recovered safely. Actual aircraft details preserve the planned aircraft.

For this application step, another employee's existing arrival is visible but read-only, and the endpoint rejects adding competing input. The domain's per-employee collection and existing historical records remain unchanged. The viewer's own record is displayed first when present, otherwise the accepted record or earliest record. Only the submitting staff identity can correct its own input. Adding other employees' submissions remains deferred.

Android stores valid input in its account/API-scoped Room arrival queue before requesting an upload. Pending input survives process recreation and replaceable flight-cache refreshes, and its submitter can continue editing it offline. The queue keeps the latest desired input separately from any transmitted request awaiting acknowledgment. Unsent edits replace only the desired input; an acknowledged earlier request advances a newer local correction to its returned version. The additive Room 4 → 5 migration preserves existing pending requests for replay before any correction. Reconnect, session/foreground/manual flight refresh, and a dedicated WorkManager job retry uploads; transport failures keep the original request/version. Conflicts and rejected requests retain their data for review instead of rebasing automatically. The form can explicitly reload a live flight for review and then save a replacement; Sync Center exposes retry and confirmed discard, including for flights no longer eligible to open. Sign-out/account switch waits for authenticated uploads before clearing the queue. Successful saves publish the existing flight-refresh hint; other employees see the saved details after refresh. While offline, their view reflects the last successful read.

## Departure submissions

`Flight.DepartureSubmissions` owns `FlightDepartureSubmission` entities, each containing a `DepartureDetails` value object. ATD, customer signature, and the handling employee are required. ATD is stored in UTC. Remarks are optional, with whitespace-only values becoming null. The signature uses the shared `CustomerSignature` value object containing `FileName`, `StorageKey`, `ContentType`, positive `SizeBytes`, and required UTC `SignedAtUtc`. File names use basename normalization and a 255-character limit; keys and content types are limited to 500/100 characters. Normal departure requires the signature, while RTR departure allows it to be absent. Each departure record copies its signature value independently, preserving separate EF ownership even when callers reuse an input value. File bytes remain outside the relational model. The departure save workflow below stores PNG signature bytes through the existing `IFileStorage` boundary and retains this metadata in the departure value object.

As with arrivals, each submitting `StaffMemberId` has at most one departure submission per flight, and the handler can differ from the submitter. Updates preserve submission identity; unchanged details are a no-op. The first submission is accepted automatically; adding another employee's submission clears acceptance, and multiple records remain unaccepted pending the later approval workflow. Arrival and departure acceptance are independent.

### Departure save workflow

`PUT /api/v1/operations/flights/{id}/departure` requires `operations.flights.operate`, `If-Match` with the current eight-byte rowversion, and the same active staff/station, membership/category, and rolling-window boundary as mobile details. Its JSON request contains `atd`, optional `signatureContent` (base64 PNG), optional UTC `signatureSignedAtUtc`, optional `remarks`, and `acknowledgeConflictingSubmission` (default false). The first save requires signature content and a non-default signing time. An owner correcting an existing departure may omit both signature fields to retain its saved signature. Supplied content is limited to 2 MiB and checked for a PNG signature before the existing `IFileStorage` boundary stores it; storage keys and signature metadata are server-owned. The response contains `submission` and the current flight `rowVersion`.

Submission and handling are attributed to the authenticated linked staff member. The endpoint rejects a new competing submission when another employee’s departure exists; that record remains readable. The caller cannot submit departure while holding its own cancellation; signature requirements remain in force. Changed stale input returns `409`. An identical retry of the caller’s saved ATD, remarks, handling attribution, and signature content/signing time acknowledges the saved record even with the original version, without another write. This recovers a lost successful response and supports replay of the Android departure queue. Departure signature saving adds no general file-upload endpoint or server schema change. The scoped `GET /api/v1/operations/flights/mobile/{flightId}/departure-signatures/{submissionId}` route returns PNG bytes only for the currently visible own, accepted, or earliest submission within the existing mobile flight scope and requires `expectedUpdatedAt` to match its updated-or-created timestamp. Responses are private/no-store and expose no storage key. An optional opaque `signatureVersion` in the departure read DTO identifies the image independently of unrelated departure corrections; it adds no persisted field.

Android saves departure locally before requesting an upload, including while offline. The account/API-scoped Room departure queue stores normalized input, signing time, reviewed departure details and version, and separate desired/attempted request snapshots. Signature PNG bytes are retained in private durable files referenced by the queue rather than large base64 database columns. The additive Room 5 → 6 migration preserves existing arrival input. Save closes the form after its local write succeeds; reopening pending input restores its ATD, remarks, and signature, and newer edits cannot replace an unacknowledged request.

Arrival input on the same flight uploads first. Only actual acknowledgments of the account’s own arrival requests may advance a queued departure version; an advanced version requires a live departure comparison, without adopting the read’s rowversion. Once a departure attempt is prepared, retries keep its exact input, signature and version until acknowledged. Acknowledgment of an earlier departure advances a newer desired correction; external conflicts still require explicit review. Network-constrained WorkManager jobs and session, reconnect, foreground, poll and manual refreshes drain the queues. Transient failures stay pending; conflicts and rejected input remain available in Sync Center for reload/review, retry or confirmed local discard. Account transitions wait for in-flight requests before clearing device intent and signature files. Android previews pending private PNGs and uses an account/API/flight/submission/version-scoped private cache for fetched or acknowledged signature images. The dialog pins its original preview; Replace starts new ink, Use confirms it, and Keep/Close/Back preserve the original. Bounded Undo covers strokes, Clear, and replacement. An exact upload acknowledgment caches the PNG before queue-file cleanup, allowing the same signature to remain viewable offline.

The ATD field starts blank when no saved departure exists; tapping it seeds the date/time picker from STD, and a clear action removes the input. Only a submission’s owner can correct it. Other employees’ arrival and departure details appear read-only in separate cards at their normal Arrival and Departure positions, with Services and Tasks between them. The summary layouts and viewing rules are preserved. Gray icon-led receiving and handling employee captions appear inside their respective cards; the submitter’s own submissions retain the normal fields. The departure card shows a customer-signature thumbnail, or a hyphen when unavailable, bounded to the existing 22sp second line above the handling employee caption. The flight details sheet combines visible ATA/ATD and receiving/handling staff names in Actual Details. Completed local arrival and departure saves overlay the current account’s desired queued values immediately, with a Saved on this device caption, including while synchronization is pending or requires review. This display projection does not change server submissions, acceptance, ownership, or rowversions. Discard restores the server details, and acknowledged synchronization replaces the local overlay. Without local input, selection mirrors arrival’s own submission, accepted submission, then earliest submission order. This workflow does not persist performed services, tasks, or their attachments.

## Cancellation submissions

`Flight.CancellationSubmissions` owns `FlightCancellationSubmission` entities, each containing a submitting employee snapshot, a `CancellationDetails` value object, acceptance state, and audit metadata. `CanceledAtUtc` is required, rejects the default timestamp, and is normalized to UTC. Remarks are optional, trimmed, and stored as null when blank.

`Flight.SubmitCancellation` keeps at most one submission per submitting `StaffMemberId`. Corrections update only that employee's submission, preserving its identity and other employees' inputs; identical details are a no-op. A sole submission is accepted automatically. Adding another employee's submission clears acceptance, and multiple records remain unaccepted pending the later approval workflow.

Cancellation and arrival/departure are mutually exclusive per submitting employee. An employee with an arrival or departure cannot submit cancellation, and an employee with a cancellation must revert it before submitting arrival/departure. Different employees may report opposing outcomes after explicit confirmation; neither report overwrites the other. The existing global guards remain for performed services, tasks, and return-to-ramp: their presence prevents cancellation, and any cancellation, including an unaccepted one, prevents their mutations, including resource, performer, and attachment changes. Planning and roster behavior is unchanged; no general reopen or terminal-status workflow is introduced.

### Cancellation save and revert workflow

`PUT /api/v1/operations/flights/{id}/cancellation` requires `operations.flights.operate`, the current `If-Match` rowversion, and the existing active staff/station, membership/category, and rolling-window mobile boundary. The request is `{canceledAtUtc, remarks, acknowledgeConflictingSubmission}`; acknowledgement defaults to false. The response is `{submission, rowVersion}` with attributed cancellation details. Cancellation requires confirmation when another employee has submitted arrival/departure. Arrival and departure requests also accept `acknowledgeConflictingSubmission` and require confirmation when another employee has canceled. Confirmation authorizes the opposing report, not another employee's data changes, and does not bypass a stale version. An identical lost-success retry can acknowledge the existing submission without another write. The same employee's work-versus-cancellation conflict is rejected even when acknowledgement is true.

`DELETE /api/v1/operations/flights/{id}/cancellation/{submissionId}` reverts only the authenticated employee's exact cancellation ID under the same permission/scope and `If-Match` rules. Its response contains remaining `cancellationSubmissions` and the current `rowVersion`. Repeating an already completed revert is idempotent; a delayed request cannot remove a newer replacement. Reversion leaves other employees' reports and their current acceptance state intact and does not select a new accepted report.

Android saves cancellation/reversion intent in the account/API-scoped Room version-7 `flight_cancellation_pending` queue before closing the form. Local arrival/departure and cancellation saves share a submission gate so they cannot race into opposing queues. An unsent cancellation can be reverted locally; after a possibly successful transmitted save, the queue first acknowledges the frozen attempt and then reverts its exact server ID. Pending reversion continues to block work until acknowledged. The same reconnect, foreground, refresh, and WorkManager drain retries cancellation; conflicts retain input for explicit review. A transmitted pending cancellation cannot be discarded as though unsent. Account transitions drain active uploads before clearing local intent.

The sheet hides Cancel Flight for the current employee's saved or queued work, hides Open Flight for their own saved or queued cancellation, and offers Revert cancellation. Reports from another employee instead trigger the save confirmation above. Flight detail reads include attributed `cancellationSubmissions` and `canSaveCancellation`; the compatibility `hasCancellationSubmission` flag still means any cancellation exists. These are submission capabilities and report summaries, not a generic flight status.

## Flight services

The accepted service and task business rules on `main` remain the baseline for this redesign; see the [source baseline](https://github.com/houranigit/NAGS.OperationSystem/tree/da351660897f7845fd70e1f191bd5e0f22346939/src/Modules/Operations/Operations.Domain). The agreed changes are direct flight ownership, open work windows, stable child corrections, and task/performer notes. A change in ownership or application workflow does not by itself remove an existing resource rule.

`Flight.Services` exposes normal actual `FlightService` records separately from `PlannedServices` and return-to-ramp work. The mapped `ServiceRecords` collection contains both normal and return-to-ramp services. Each records a service snapshot, a `TimeWindow`, optional customer reference number, and optional notes. Optional text is trimmed and becomes null when blank; customer references are limited to 200 characters and notes to 2,000. Unknown services require notes, and Aircraft Per Landing cannot be recorded as an actual service. A window has a required UTC start and an optional UTC end; a supplied end must be at or after the start. Repeated occurrences of the same service are allowed.

`TimeWindow` contains only the start and end instants and is also used by employee work periods. On the service, `CreatedByUserId` is the single source of truth for the starter, since adding the service starts it; there is no separate starter field. `EndedByUserId` is null for an open window. Supplying or correcting the end time records the acting user; clearing the end clears that identity. An initially closed service records its creator as both starter and closer. Changes that keep the same end time, including notes, performer, or attachment edits, preserve the closer. The closer is a recording-user identity, separate from the employees performing the service and the user who last edited it.

Each service owns at most one performer record per employee, containing an employee snapshot and that employee's own time window. Employee periods must start at or after the service start; when a service end is supplied, neither the employee start nor a supplied employee end may exceed it. Parent-window corrections revalidate existing periods. Services, performers, and attachments have stable identities. Parent-scoped updates preserve other records and attachments; removing a performer or attachment affects only that record. Service records and attachments retain actor and timestamp metadata. Services have no acceptance flag or per-employee submission selection; review remains a later workflow. This slice adds no schedule bounds or accepted-arrival prerequisite.

Each service or task allows at most ten attachment entities. `AttachmentDetails` requires an explicit `Kind` (`Image = 0`, `Voice = 1`, `Document = 2`), file name, storage key, content type, and positive byte size. File names are reduced to the basename and truncated to 255 characters; storage keys are limited to 500 characters and content types to 100. Attachment records retain their parent, uploading user, and timestamp. Bytes belong in file storage through the existing `IFileStorage` boundary. This slice changes metadata only: it implements no upload, download, physical file deletion, MIME allowlist, or file-byte size cap.

## Flight tasks

`Flight.Tasks` exposes normal `FlightTask` records; the mapped `TaskRecords` collection contains both normal and return-to-ramp tasks. Each task has a required `TaskType` (`Major` or `Minor`), a `TimeWindow`, optional ATA chapter snapshot, optional customer reference number, and optional notes. ATA chapter snapshots contain the chapter ID, code, and title. MasterData retains catalog ownership; these snapshots add no cross-module foreign keys. Optional text is trimmed and becomes null when blank; customer references are limited to 200 characters and notes to 2,000.

Each task owns tool, material, general-support, and performer records with optional notes of at most 2,000 characters. A resource ID may appear only once per resource collection on a task, and an employee may appear only once per task. Unknown tool, material, or general-support selections require notes. Tasks and all their children have stable identities, and updates or removals are scoped to the owning task.

Resource snapshots preserve their catalog `CalculationType`: `Quantity = 0` or `Duration = 1`. Tools default to Duration; materials and general supports default to Quantity. `ResourceUsage` must match that snapshot and contain exactly one branch. Quantity usage requires a positive value fitting `decimal(18,2)` (at most `9999999999999999.99`) and forbids both duration times. Duration usage forbids quantity, requires a valid UTC start, and allows an optional valid UTC end at or after the start. SQL check constraints retain the same branch and snapshot-type agreement.

Resource duration windows and employee periods must start at or after the task start. A supplied child end cannot exceed a supplied task end; employee starts also cannot exceed a supplied task end. Employee periods use `TimeWindow`; resource periods use `ResourceUsage`. Parent-window corrections revalidate all existing periods. Open task windows have no upper end bound until an end is supplied. No schedule-bound policy is added.

As with services, `CreatedByUserId` is the sole starter identity. `EndedByUserId` is null while the task window is open; initially closed tasks use the creator as closer. Supplying or correcting the end records the acting user, clearing the end clears the closer, and other edits preserve it. Attachments use the existing `AttachmentDetails` file metadata and upload actor/timestamp fields; file bytes remain outside the relational model. Tasks have no acceptance flag or per-employee submission selection.

This slice adds task models and persistence, including typed quantity/duration capture; it does not calculate prices, consume stock, or bill resources. Task application workflows, APIs, application screens, offline writes, file transfers, and approval selection remain deferred. Main's submission/completion requirement that a service have a performer, and application checks for catalog eligibility, account/station access, and payload/file validation, remain responsibilities to integrate at their application boundaries. In-progress domain records can be built incrementally; this model slice does not claim those later application workflows are implemented.

## Return to ramp

`Flight.ReturnToRamps` owns `FlightReturnToRamp` occurrences. Starting one requires any flight departure submission, including an unaccepted submission; it does not require an approval selection. A flight may have only one open occurrence. Each occurrence has one required `RtrArrivalDetails` value object and one optional `RtrDepartureDetails` value object, rather than per-employee submission lists. Arrival requires a UTC time and receiving employee; departure requires a UTC time and handling employee. Remarks on either record are optional, trimmed, and limited to 2,000 characters.

Departure closes the occurrence and cannot precede its arrival. There is no additional comparison with a flight departure time or another occurrence's times. The occurrence's stable `Sequence` comes from the persisted `LastReturnToRampSequence` counter, is retained on corrections, and is never reused after removal. Creation and edit actors/timestamps are retained, and `EndedByUserId` records who supplies or corrects its departure.

Return-to-ramp services and tasks reuse the existing work models and all retained service/resource rules. Each has an immutable optional `ReturnToRampId`; null identifies normal work. Occurrence activity windows must stay within its arrival/departure window. Closing requires at least one service or task, a closed window and at least one performer on every service/task, and closed employee periods. Resource usage retains its Quantity/Duration rules, including optional duration ends. Valid corrections to closed occurrences are allowed, but arrival, departure, and child changes validate retained work before mutation. Closing does not introduce a new approval or authorization workflow.

The departure signature is optional and uses the same `CustomerSignature` value object as normal departure. When supplied, all five fields are validated: `FileName`, `StorageKey`, `ContentType`, positive `SizeBytes`, and required UTC `SignedAtUtc`. The same basename normalization and 255/500/100-character limits apply, and the value is copied independently into its owning departure record. The optional signature and optional RTR departure remain absent when not recorded; shared signature validation does not make either mandatory. These are metadata references to the existing file-storage boundary, without upload, download, physical deletion, or signing UI.

## Operational persistence boundary

Domain guards use loaded collections. Write callers must load all three submission collections, all `ServiceRecords` with performers/attachments, all `TaskRecords` with tools/materials/general supports/performers/attachments, and `ReturnToRamps` with their work graph. The public `Services` and `Tasks` views are not mapped navigations and exclude occurrence work. For an existing tracked flight, changes anywhere in these attached graphs, including nested edits or removals, force the flight's rowversion check in synchronous and asynchronous saves, even when `UpdatedAtUtc` is unchanged. Return-to-ramp sequence uniqueness and the single-open-occurrence rule are also indexed in SQL. Composite occurrence/flight foreign keys prevent work from being grouped under another flight's occurrence. Flight remains the cascade-delete path; occurrence relations use `NoAction` to avoid multiple cascade paths. There is no database constraint enforcing cancellation exclusivity across tables, so direct SQL bypasses it. Arrival uses the explicit review workflow above; offline conflict resolution for other operational mutations remains deferred.

Arrival adds the API/mobile save and queue described above; departure adds the save API, signature storage, and Android local queue workflow. The remaining models add no operational API, portal or mobile writes, file transfer, approval selection, return-to-ramp application workflow, task application workflow, or billing workflow. Flight detail reads include arrival and departure submissions alongside planning details. Flight statuses, further prerequisites, and chronology policies remain for the later workflow discussion.

## Scheduling and validation

The existing flight grid and scheduling dialog support a single flight, multiple selected dates, and basic schedule edits. Required fields are customer, station, operation type, flight number, arrival/departure, and at least one planned service. Aircraft type and assigned staff remain optional. Staff assignments require the existing assignment permission and active staff at the selected station.

The scheduling input shows the customer code as a separate prefix. Flight numbers accept 1–4 digits, optionally followed by either one letter or `/` and one or two route digits; a letter and a route cannot be combined. The dialog checks this format and required details locally on the first Next click. The customer's IATA code may be entered or omitted; it is never required in the input. The backend adds it when missing, validates the complete number, and normalizes letter case on single creation, batch creation, and number changes. For customer `SV`, `123A` or `SV123A` stores `SV123A`, while `123/01` or `SV123/01` stores `SV123/01`. Whitespace, dashes, additional letters, more than four flight digits, empty routes, and routes longer than two digits are rejected. The 12-character storage limit remains, and the grid displays the saved number directly. Existing stored numbers are not rewritten, and planning-only edits preserve them. Number changes use the customer's saved snapshot IATA code.

Aircraft Per Landing remains an exclusive planned designation and cannot be combined with other planned services or assigned staff. Ad Hoc is unavailable for scheduling. All operational date/time inputs in web and Android use the station’s configured IANA `TimeZoneId`, including scheduling and service/task/resource periods. Flight schedules and operational times are displayed in that same station zone without time-zone captions. UTC instants remain the storage and API contract. Recurring scheduling resolves the current station zone on the server for each selected date and preserves overnight departures; any legacy request `TimeZoneId` is ignored. Invalid or ambiguous local times fail validation rather than silently shifting the schedule. Station time zones are mandatory. The migration supplies `Etc/UTC` as a generic value for existing rows; administrators must replace that placeholder with the airport’s correct zone before entering local operational times. Station and flight contracts require valid zone metadata; clients use the station clock directly without configuration prompts. Older cached flight details missing required metadata follow the existing refresh policy. Flight read responses expose the current station zone, and mobile caches it with the flight for offline operation; a station-zone change refreshes flight metadata. Audit and notification metadata retain their existing presentation rules.

## User notifications

Scheduling one flight with assigned staff, adding employees through roster replacement or the planning editor, and inviting employees queue transactional `FlightEmployeeAssigned` events for newly added employees only. Invitations use `EmployeeInvitedToFlight`; other additions use `StaffAssignedToFlight`. Repeated selections and removals are silent. A batch that creates multiple flights queues one `FlightScheduleUpdated` event per distinct assigned employee instead of one notification per flight; a batch with one distinct date uses the single-flight assignment behavior. Editing flight times alone does not produce a schedule-update notification.

Notifications resolves the employee's linked user, suppresses assignment/bulk self-notifications and unlinked recipients, saves bilingual inbox entries, and attempts the existing SignalR/FCM transports. Transport retries reuse the event/notification ID and do not reverse an accepted flight change.

Mobile and portal present an English-only, single notification feed: **New** first, then older entries grouped by local date. New entries keep their background tint during the current visit. Opening the inbox acknowledges all kinds through the newest observed creation timestamp; newer entries remain unread until observed. Cached history and pending read cutoffs survive reconnects. Cards append a bold short relative age to the message and use distinct kind colors. Only the explicit card action navigates. Mobile labels it **View** and shows it solely when the notification flight reference is present in the local **My Flights** tab; it adds no notification-kind or reminder-age gate and makes no availability API or pre-open validation request. The portal retains Operations availability checks in batches of at most 100 IDs under its existing flight-read scope and rechecks before navigation. The normal detail loader retains its access checks and mobile offline saved-detail requirements. A partial left swipe reveals compact red **Delete**; a full swipe invokes the same archive operation automatically. Failures restore the row and successful removal animates. Paging is automatic and notification rows are virtualized.

Flight reminders retain `main`'s durable 12-hour, 2-hour, and 30-minute milestones before STA. `Operations:FlightReminders` enables the scanner by default, polling every 60 seconds with a 13-hour enrollment horizon and five-minute enrollment lateness tolerance. Milestones already too old at enrollment are skipped. Dispatch skips superseded milestones, removed assignments, missing flights, changed STA snapshots, and expired STA. Notifications rechecks live eligibility before persistence, delivery, and transport retries.

This model has no terminal flight status. Any cancellation submission, including competing unaccepted submissions, suppresses reminder enrollment and delivery, independently of which employee submitted it and whether an opposing arrival/departure report also exists. Arrival and departure submissions do not introduce a completion status. Reminder schedules belong to Operations; inbox entries and device delivery remain owned by Notifications. Reminder scanning and transactional outbox dispatch must both be enabled for delivery.

## Authorization and API

Retained permissions are `operations.flights.view`, `view-station`, `schedule`, `update`, `assign`, `invite`, and `operate`. Existing staff roles must be granted `operations.flights.operate` explicitly; arrival saving does not reuse planning-update permission. Existing account/station scope remains enforced on the backend. Viewer accounts are read-only; station staff see assigned flights and station-wide Per Landing flights unless granted station-wide visibility. Customer contacts have no Operations access.

All flight routes are under `/api/v1/operations/flights`:

| Method | Route | Behavior |
|---|---|---|
| GET | `/` | Filtered, sorted, paged flight register |
| GET | `/{id}` | Flight planning details, arrival/departure/cancellation submissions, and rowversion |
| PUT | `/{id}/arrival` | Save the authenticated employee's arrival within mobile scope |
| PUT | `/{id}/departure` | Save the authenticated employee's departure and signature within mobile scope |
| PUT | `/{id}/cancellation` | Save the authenticated employee's cancellation within mobile scope |
| DELETE | `/{id}/cancellation/{submissionId}` | Revert the authenticated employee's exact cancellation within mobile scope |
| GET | `/mobile/{flightId}/departure-signatures/{submissionId}` | Read the visible departure PNG at the expected updated-or-created version within mobile scope |
| GET | `/mobile` | Station-linked mobile feed, optional category, rolling 24-hour overlap window |
| GET | `/mobile/{id}` | Details only for a currently eligible mobile flight |
| GET | `/mobile/customer-logos/{customerId}` | Customer logo for a currently eligible mobile flight |
| GET | `/mobile/{id}/invitation-options` | Invitation options within the mobile scope |
| POST | `/mobile/{id}/invite` | Existing add-only invitation behavior within the mobile scope |
| GET | `/customer-logos/{customerId}` | Customer logo when at least one flight for that customer is visible to the caller |
| POST | `/` | Schedule one flight |
| POST | `/bulk` | Schedule selected dates |
| PUT | `/{id}` | Update scheduled details |
| POST | `/{id}/change-number` | Change the current number |
| POST | `/{id}/assign` | Replace assigned staff |
| GET | `/{id}/invitation-options` | Active, unassigned staff at the flight station |
| POST | `/{id}/invite` | Add selected employees without replacing the roster |

Edits and invitations retain the existing `If-Match` rowversion precondition. Invitations require `operations.flights.invite`, an administrator or station-staff account, and access to the flight. They accept only active staff at that flight's station and are unavailable for Per Landing flights. Invitations add distinct employees immediately to the existing roster; repeated selections do not replace assignments or create duplicate invitation events. A stale version that would add employees fails without changing the roster. The retained invitation event queues the existing bilingual inbox/push notification for linked recipients, suppressing self-notifications; transport delivery remains separate from the accepted flight change.

Customer logo reads require `operations.flights.view` and the existing flight visibility scope. Operations checks for a visible flight before reading logo content through the MasterData-owned reader contract. MasterData retains logo storage and customer-management permissions. The register includes the current opaque `customerLogoVersion` from a batched MasterData read; `none` identifies an absent logo. Logo responses include the actual version as an ETag and accept an optional `expectedVersion`, returning `412` if it changed. Missing logos or files return `404` for the card's flight-icon fallback. Customer options expose the same `logoVersion` for catalog synchronization.

Operations work-order, legacy mobile BFF, timeline, lifecycle, reporting, and dashboard endpoints are removed. The shared change hub remains owned by the API host because MasterData publishes catalog hints and Operations publishes basic-flight hints.

## Android baseline

Android uses the bounded `/api/v1/operations/flights/mobile` feed and matching details, logo, and invitation routes. As on `main`, mobile requires an active linked staff member and active station; administrator/viewer accounts without a station-linked employee cannot use this feed. Station is resolved from the employee record. Every read requires an inclusive overlap of STA–STD with server now ±12 hours. The three server-filtered categories are: My Flights (assigned to the caller, excluding Per Landing and AdHoc), Per Landing (station flights without requiring assignment), and AdHoc (fixed Ad Hoc operation type, created by the caller). AdHoc takes precedence for legacy mixed-designation records. Station-wide permission does not widen My Flights. Portal reads retain the broader authorization described above.

The light home shell has four bottom destinations, the three Flights tabs, and an inline tab-scoped search toolbar. Its expanding search pill hides the tabs; a keyboard accessory selects My Flights, Per Landing, or AdHoc while retaining the query. Clear and Close restore normal cached tab data, and the same station/window scope applies to results. Hand Over flights, Page 3, and Page 4 remain placeholders. Initial and next-page reads use skeletons, retaining cards during refresh. Android displays schedules in the station time zone and supports authorized online invitations; it does not create or schedule flights. Customer logo files persist privately per API/account across flights and process restarts. Customer/flight metadata reconciliation updates changed versions and removes explicit absent logos; unchanged refreshes reuse saved images.

The sheet and form use Ops Type with two spaces before its bold value and a right-aligned submission-progress badge. Sheet action faces are 32dp with 16dp icons inside 48dp touch slots separated by 2dp; only available actions occupy slots. Their overlay beside the flight number preserves the normal spacing above the customer name. The selected action expands from its own slot across the fixed 148dp toolbar, preserving the anchored spring motion and the original three-slot expanded width. The form's scheduled-aircraft caption shares the date's style and baseline, while the sheet's Schedule Details shows planned aircraft/N/A with the station-code caption.

Flight reads prefer the live bounded endpoint and fall back to the last successful scoped snapshot and previously opened details. Full synchronization requests only the eligible union, revalidates cached details, and removes no-longer-visible flights. Offline paging and visible details recheck the rolling window; expired data is pruned even without a new server event. Old unrestricted snapshots and orphan detail rows are discarded before offline access. Newly confirmed station metadata removes the old station cache immediately, even if the remaining sync fails; incomplete pages never become an offline snapshot. Details never opened online need a connection. The Flights Sync Center card reports count, freshness, duration, and errors; cached reads are identified on screen. Invitations require a connection and fresh eligibility checks, with no offline submission queue. Identity sign-in, optional enrolled MFA, token refresh, profile, and Notifications remain existing capabilities.

Shared MasterData catalog synchronization remains a separate mobile capability. Android caches customers, aircraft types, services, tools, materials, general supports, ATA chapters, and station staff from the existing `/api/v1/masterdata/{catalog}/options` routes. Those requests retain their reference-lookup or per-catalog view permission and scope checks; flight access does not imply catalog access. Staff synchronization uses `/api/v1/masterdata/staff-members/options`: station-staff accounts receive active staff only from their own station, global readers keep their existing scope, and customer contacts have no staff access. The Station staff card reports that cache; flight invitation options remain live and independently enforce eligibility. Sync Center, opened from profile, retains the established diagnostics layout: network online/offline state, live-channel state and last catalog event, cached counts, last successful refresh, measured duration, errors, and a manual refresh action. Sign-in/token refresh, foreground entry, network or catalog-hub reconnection, a five-minute process-active poll, and manual refresh reload all catalogs. Live catalog-change hints reload only the affected catalog and leave the other catalogs' sync metadata unchanged; ordinary staff changes therefore refresh staff only. Operations changes refresh flights only; staff station/active changes and station active changes also invalidate flight visibility. Open flight views refresh after successful flight sync. MasterData publishes a hint after a successful create, active lookup-field edit, or real activation/deactivation; customer logo replacements also publish customer hints, including for inactive customers. Byte-identical logo uploads, other inactive edits, lookup-irrelevant changes, no-op transitions, and failed writes do not invalidate catalogs. Network failures retain the last successful catalog snapshot; permission denial removes the denied snapshot. Catalog access does not grant flight access or authorize arrival or departure writes; those retain the Operations permission and scope checks above.

The former `operations.db` file and dormant drafts/queued work remain unopened. Shared catalogs, separate basic-flight snapshot/detail tables, and durable operational queues use `shared-catalogs.db` Room version 7, keyed by API environment and authenticated account and cleared on sign-out/account changes. The additive version 2 → 3 migration preserves all catalog rows. All preserve existing snapshots and queued input; the old work-order queue is not read or replayed. Failed connections retain good snapshots; authorization denials evict denied flights. Offline reads reflect the last successful access check until the device reconnects. Notifications use the separate `operations-baseline.db` Room database. Startup cancels the retired WorkManager outbox chain/tag, and its retained worker entry point is inert. A notification flight link resolves the current basic flight details through the scoped API. ## Database change

Submission, performed-service, task, and return-to-ramp storage uses additive Operations migrations that preserve existing flight planning and operational data and do not change another module's schema. Cancellation adds an initially empty `operations.flight_cancellation_submissions` table. Performed services add Operations tables for service records, performer periods, and attachment metadata. Tasks add Operations tables for task records, tool/material/general-support usage, performer periods, and attachment metadata. Return to ramp adds an occurrence table, a flight sequence counter, and nullable occurrence ownership on existing service/task rows; existing work remains normal work with no occurrence ID. Generating these migrations does not apply them to configured databases. The task migration also restores the service text/attachment limits and employee uniqueness. It checks existing service data before narrowing columns or adding indexes, and stops with a diagnostic if records violate restored rules. It preserves existing IDs, storage keys, and actor/timestamp metadata; existing attachment display names are normalized and attachment kinds are derived from their MIME types. It does not delete conflicting records or truncate notes, references, or storage keys.

The shared-signature migration is additive after the published migrations and adds required `CustomerSignatureFileName` and `CustomerSignedAtUtc` columns to normal flight departure submissions. For those legacy normal-departure rows only, the file name is derived from the existing storage key basename (normalizing both slash styles), truncated to 255 characters, and set to `customer-signature` when the basename is empty. `CustomerSignedAtUtc` is backfilled from the submission's `CreatedAtUtc`: this is a documented historical fallback to recording time, not a claim about the actual signing time. Preflight stops on legacy keys over 500 characters, content types over 100 characters, or a default submission creation time, rather than changing file references or fabricating a time. Existing RTR signature metadata is already complete and remains untouched.

Keep the historical `main` EF migrations unchanged. `Operations_FlightSchedulingBaseline` preserves the existing flights, direct `flight_planned_services`, and `flight_assigned_employees` rows in place, and removes retired work-order, mobile, reminder, history, status, contract, and merge storage plus pending event envelopes for retired Operations contracts. The retained `FlightEmployeeAssigned` invitation contract and platform audit envelopes are preserved. The migration does not require a HandOver operational graph. It does not alter another module's schema or delete stored file blobs.

`Operations_RestoreFlightNotifications` subsequently recreates Operations-owned durable reminder schedules with unique flight/employee/STA/milestone identities and dispatch/cleanup indexes. Existing flight, roster, submission, and notification data is preserved. Historical reminder rows removed by the scheduling baseline are not replayed; the scanner enrolls currently eligible assignments.

This migration intentionally discards work-order/workflow data. Development startup migrations are disabled. Review the SQL and back up an existing database before applying the reset and running the API against that database. Restoring the previous application requires restoring its database backup; the reset migration cannot reconstruct the removed operational history. Verification uses disposable local SQL databases, never a configured remote database.

The isolated current-branch Docker target is `OperationsSystemOperationModuleMain`, initialized from a main-compatible database copy. The earlier HandOver-derived `OperationsSystemOperationModule` database remains preserved under its original name and is not overwritten or reused for this migration chain. Main/release remains a separate stable environment; see the [local environment runbook](../architecture/production-runbook.md#concurrent-local-environments).
