# Operations Module Foundation

This is the entry point for the current Operations module. This branch starts from `main` with a flight scheduling baseline: maintain a flight register, create one flight, schedule the same flight on selected dates, and invite employees onto an existing flight. Arrival has an API and local-first Android save workflow. Departure has a save API with customer-signature storage and a local-first Android save workflow. Cancellation has save/revert APIs and a local-first Android workflow. Performed flight services now have scoped APIs and local-first Android saving with durable drafts and attachments. Flight tasks and return-to-ramp occurrences retain domain and persistence models; bounded mobile list reads expose their work counts and RTR summary metadata for flight cards. The Android client supports flight viewing, details, arrival/departure and service saving, cancellation saving/reversion, and employee invitations; scheduling remains in the web portal. HandOver implementation is excluded. Further operational APIs and application workflows will be designed and implemented individually later.

## Flight data and ownership

`Flight` owns customer, station, operation type, flight number, scheduled arrival/departure, optional aircraft type, planned services, assigned employees, operational submissions, performed services, tasks, and return-to-ramp occurrences. MasterData remains authoritative for reference records; Operations validates selections through its existing readers and stores snapshots. Planned services and assigned employees are direct flight collections.

Creation/update timestamps, creator ID, and SQL rowversion support persistence and concurrency. Android details and recording forms derive their display-only submission-progress badge from existing submissions and the current account’s durable local queues. The labels cover Draft, submitted arrival/departure/cancellation, pending synchronization, cancellation reversion awaiting sync, and needs review. Local cancellation intent takes precedence; a queued work correction remains visibly pending. The badge adds no stored status or approval state. There is one current scheduled flight number. Beyond the submission, performed-service, task, and return-to-ramp models described below, a stored flight status, original-number history, contract placeholders, merge metadata, other actual work, work orders, handover, review, approval, timeline, file transfers, and automatic work creation remain outside this scope. Platform audit capture remains enabled independently of a flight history feature.

## Arrival submissions

`Flight.ArrivalSubmissions` owns `FlightArrivalSubmission` entities, each containing an `ArrivalDetails` value object. ATA, actual aircraft type, aircraft tail number, and the receiving employee are required. Customer work reference number and remarks are optional; whitespace-only optional values become null. ATA is stored in UTC and is not constrained by the scheduled arrival or departure. Actual aircraft details do not replace the flight's planned aircraft type.

Each submitting `StaffMemberId` has at most one arrival submission per flight. Updating that employee's submission preserves its identity; the receiving employee can differ from the submitter. A sole submission is accepted automatically. Adding a second employee's submission clears acceptance, and submissions remain unaccepted while multiple records exist. Selecting an accepted record belongs to a later approval workflow.

### Arrival save workflow

Open Flight opens the existing flight form. Its top-right Save retains durable arrival, departure, service, and Task input on the device through separate queues. Unstarted service and task rows remain local form drafts; cancellation uses its separate workflow below. The initial submission and receiving employee are both attributed server-side to the authenticated linked staff member. ATA, actual aircraft type, and tail number are required; reference and remarks remain optional. A new form leaves ATA blank until the user taps it, which seeds the picker from the current station date/time; saved and pending ATA values remain intact. Validation follows the existing arrival model without adding schedule bounds or arbitrary text limits. Android also requires a current eight-byte rowversion and an aircraft from its cached active catalog; the server rechecks catalog eligibility and mobile flight access.

`PUT /api/v1/operations/flights/{id}/arrival` requires `operations.flights.operate` and `If-Match`, with the same active staff/station, membership/category, and rolling-window boundary as mobile details. Missing/invalid preconditions and invalid fields use the existing validation response (`400`); stale changes return `409`. The response contains the saved arrival and current flight rowversion. An identical retry of the caller's existing input acknowledges the saved record without another write, even with the original version, so a lost success response can be recovered safely. Actual aircraft details preserve the planned aircraft.

Another employee's existing arrival is shown as a submitted summary. An employee assigned to that flight may open Update arrival details… to correct that exact record in a separate prefilled page. Assigned employees have equal authority to update arrival and departure submissions regardless of who submitted them. Both save requests accept optional `targetSubmissionId`; omitting it updates the caller's own submission when present, otherwise the sole existing submission. When multiple other submissions exist, the caller must identify the target. The server rechecks flight assignment for another employee's submission, existing operate permission/mobile scope, cancellation and work-period invariants, and the flight rowversion. Corrections preserve the submission ID, original submitter, receiving/handling employee, creation timestamp and acceptance. The viewer's own record is displayed first when present, otherwise the accepted record or earliest record. Creating competing submissions remains deferred.

Approval locking and administrator unlocking are TODO features. Once approval is implemented, approval will lock flight updates for every assigned employee, including the original submitter, until an administrator unlocks the flight. The existing submission `IsAccepted` flag is not approval and does not lock editing.

Android stores valid input in its account/API-scoped Room arrival queue before requesting an upload. Pending input survives process recreation and replaceable flight-cache refreshes, and its submitter can continue editing it offline. The queue keeps the latest desired input separately from any transmitted request awaiting acknowledgment. Unsent edits replace only the desired input; an acknowledged earlier request advances a newer local correction to its returned version. The additive Room 4 → 5 migration preserves existing pending requests for replay before any correction. Reconnect, session/foreground/manual flight refresh, and a dedicated WorkManager job retry uploads; transport failures keep the original request/version. Conflicts and rejected requests retain their data for review instead of rebasing automatically. The shared Review editor loads online values, or identifies a cached snapshot offline, and keeps rejected local input in a separate card; Sync Center exposes retry and confirmed discard, including for flights no longer eligible to open. Sign-out/account switch waits for authenticated uploads before clearing the queue. Successful saves publish the existing flight-refresh hint; other employees see the saved details after refresh. While offline, their view reflects the last successful read.

## Departure submissions

`Flight.DepartureSubmissions` owns `FlightDepartureSubmission` entities, each containing a `DepartureDetails` value object. ATD, customer signature, and the handling employee are required. ATD is stored in UTC. Remarks are optional, with whitespace-only values becoming null. The signature uses the shared `CustomerSignature` value object containing `FileName`, `StorageKey`, `ContentType`, positive `SizeBytes`, and required UTC `SignedAtUtc`. File names use basename normalization and a 255-character limit; keys and content types are limited to 500/100 characters. Normal departure requires the signature, while RTR departure allows it to be absent. Each departure record copies its signature value independently, preserving separate EF ownership even when callers reuse an input value. File bytes remain outside the relational model. The departure save workflow below stores PNG signature bytes through the existing `IFileStorage` boundary and retains this metadata in the departure value object.

As with arrivals, each submitting `StaffMemberId` has at most one departure submission per flight, and the handler can differ from the submitter. Updates preserve submission identity; unchanged details are a no-op. The first submission is accepted automatically; adding another employee's submission clears acceptance, and multiple records remain unaccepted pending the later approval workflow. Arrival and departure acceptance are independent.

### Departure save workflow

`PUT /api/v1/operations/flights/{id}/departure` requires `operations.flights.operate`, `If-Match` with the current eight-byte rowversion, and the same active staff/station, membership/category, and rolling-window boundary as mobile details. Its JSON request contains `atd`, optional `signatureContent` (base64 PNG), optional UTC `signatureSignedAtUtc`, optional `remarks`, optional `targetSubmissionId`, and `acknowledgeConflictingSubmission` (default false). The first save requires signature content and a non-default signing time. A correction to an existing departure may omit both signature fields to retain that target's saved signature. Supplied content is limited to 2 MiB and checked for a PNG signature before the existing `IFileStorage` boundary stores it; storage keys and signature metadata are server-owned. The response contains `submission` and the current flight `rowVersion`.

Every new or changed departure request also requires an End on each recorded normal service and each of its staff periods, with at least one performer per service. Only started, published service records participate; unstarted planned rows and local form drafts do not block departure, and RTR work remains separate. This check runs before signature storage or a database write. An exact retry of already accepted input is still acknowledged first, so subsequently changed work cannot invalidate recovery of a lost success response.

New submissions and handling are attributed to the authenticated linked staff member. Corrections retain the original submitter and handler; another employee must be assigned to the flight to update it. Target selection follows the arrival rules above, including updating the sole existing submission when no target is supplied. The caller cannot submit departure while holding its own cancellation; signature requirements remain in force. Changed stale input returns `409`. An identical retry of the target's saved ATD, remarks, handling attribution, and signature content/signing time acknowledges the saved record even with the original version, without another write. This recovers a lost successful response and supports replay of the Android departure queue. Departure signature saving adds no general file-upload endpoint or server schema change. The scoped `GET /api/v1/operations/flights/mobile/{flightId}/departure-signatures/{submissionId}` route returns PNG bytes for the currently visible own, accepted, or earliest submission, or an exact same-flight correction target when the viewer is assigned or its original author, within the existing mobile flight scope. It requires `expectedUpdatedAt` to match its updated-or-created timestamp. Responses are private/no-store and expose no storage key. An optional opaque `signatureVersion` in the departure read DTO identifies the image independently of unrelated departure corrections; it adds no persisted field.

Android saves departure locally before requesting an upload, including while offline. The account/API-scoped Room departure queue stores normalized input, signing time, reviewed departure details and version, and separate desired/attempted request snapshots. Signature PNG bytes are retained in private durable files referenced by the queue rather than large base64 database columns. The additive Room 5 → 6 migration preserves existing arrival input. Save closes the form after its local write succeeds; reopening pending input restores its ATD, remarks, and signature, and newer edits cannot replace an unacknowledged request.

Previously transmitted individual arrival input on the same flight resolves before dependent legacy departure attempts. New combined Saves use the atomic batch boundary below. Only actual acknowledgments of the account’s own arrival requests may advance a queued departure version; an advanced version requires a live departure comparison, without adopting the read’s rowversion. Once a departure attempt is prepared, retries keep its exact input, signature and version until acknowledged. Acknowledgment of an earlier departure advances a newer desired correction; external conflicts still require explicit review. Network-constrained WorkManager jobs and session, reconnect, foreground, poll and manual refreshes drain the queues. Transient failures stay pending; conflicts and rejected input remain available in Sync Center for reload/review, retry or confirmed local discard. Account transitions wait for in-flight requests before clearing device intent and signature files. Android previews pending private PNGs and uses an account/API/flight/submission/version-scoped private cache for fetched or acknowledged signature images. The dialog pins its original preview; Replace starts new ink, Use confirms it, and Keep/Close/Back preserve the original. Bounded Undo covers strokes, Clear, and replacement. An exact upload acknowledgment caches the PNG before queue-file cleanup, allowing the same signature to remain viewable offline.

The ATD field starts blank when no saved departure exists; tapping it seeds the date/time picker from STD, and a clear action removes the input. Other employees’ arrival and departure details appear as submitted cards at their normal Arrival and Departure positions, with Services and Tasks between them. Arrival shows the aircraft/tail and a muted W.PKG# label with its value; departure uses the removed employee-caption space for a larger signature preview, or a hyphen when unavailable. Green landing/takeoff icons precede ATA/ATD. Each card has a gray note below it with the original submitter and station-local submission timestamp in semibold. Assigned non-submitters also see the blue Update arrival details… or Update departure details… link, which opens only that target's unlocked, prefilled fields. Back discards its temporary edits; Save writes only that correction to the existing local queue, retaining unrelated work drafts in the parent form. Target identity and reviewed details travel with desired and frozen attempted requests; an unknown transmitted target cannot be replaced. After a definitive rejection, explicit Review may select the current online target while retaining its original attribution. The flight details sheet combines visible ATA/ATD and receiving/handling staff names in Actual Details. Completed local arrival and departure saves overlay the current account’s desired queued values immediately, with a Saved on this device caption, including while synchronization is pending or requires review. This display projection does not change server submissions, acceptance, ownership, or rowversions. Discard restores the server details, and acknowledged synchronization replaces the local overlay. Without local input, selection mirrors arrival’s own submission, accepted submission, then earliest submission order. Performed services, tasks, and their attachments use the separate workflows below.

## Cancellation submissions

`Flight.CancellationSubmissions` owns `FlightCancellationSubmission` entities, each containing a submitting employee snapshot, a `CancellationDetails` value object, acceptance state, and audit metadata. `CanceledAtUtc` is required, rejects the default timestamp, and is normalized to UTC. Remarks are optional, trimmed, and stored as null when blank.

`Flight.SubmitCancellation` keeps at most one submission per submitting `StaffMemberId`. Corrections update only that employee's submission, preserving its identity and other employees' inputs; identical details are a no-op. A sole submission is accepted automatically. Adding another employee's submission clears acceptance, and multiple records remain unaccepted pending the later approval workflow.

Cancellation and arrival/departure are mutually exclusive per submitting employee. An employee with an arrival or departure cannot submit cancellation, and an employee with a cancellation must revert it before submitting arrival/departure. Different employees may report opposing outcomes after explicit confirmation; neither report overwrites the other. The existing global guards remain for performed services, tasks, and return-to-ramp: their presence prevents cancellation, and any cancellation, including an unaccepted one, prevents their mutations, including resource, performer, and attachment changes. Planning and roster behavior is unchanged; no general reopen or terminal-status workflow is introduced.

### Cancellation save and revert workflow

`PUT /api/v1/operations/flights/{id}/cancellation` requires `operations.flights.operate`, the current `If-Match` rowversion, and the existing active staff/station, membership/category, and rolling-window mobile boundary. The request is `{canceledAtUtc, remarks, acknowledgeConflictingSubmission}`; acknowledgement defaults to false. The response is `{submission, rowVersion}` with attributed cancellation details. Cancellation requires confirmation when another employee has submitted arrival/departure. Arrival and departure requests also accept `acknowledgeConflictingSubmission` and require confirmation when another employee has canceled. Confirmation authorizes the opposing report, not another employee's data changes, and does not bypass a stale version. An identical lost-success retry can acknowledge the existing submission without another write. The same employee's work-versus-cancellation conflict is rejected even when acknowledgement is true.

`DELETE /api/v1/operations/flights/{id}/cancellation/{submissionId}` reverts only the authenticated employee's exact cancellation ID under the same permission/scope and `If-Match` rules. Its response contains remaining `cancellationSubmissions` and the current `rowVersion`. Repeating an already completed revert is idempotent; a delayed request cannot remove a newer replacement. Reversion leaves other employees' reports and their current acceptance state intact and does not select a new accepted report.

Android saves cancellation/reversion intent in the account/API-scoped Room version-7 `flight_cancellation_pending` queue before closing the form. Local arrival/departure and cancellation saves share a submission gate so they cannot race into opposing queues. An unsent cancellation can be reverted locally; after a possibly successful transmitted save, the queue first acknowledges the frozen attempt and then reverts its exact server ID. Pending reversion continues to block work until acknowledged. The same reconnect, foreground, refresh, and WorkManager drain retries cancellation; conflicts retain input for explicit review. A transmitted pending cancellation cannot be discarded as though unsent. Account transitions drain active uploads before clearing local intent.

The sheet hides Cancel Flight for the current employee's saved or queued work, hides Open Flight for their own saved or queued cancellation, and offers Revert cancellation. Reports from another employee instead trigger the save confirmation above. Flight detail reads include attributed `cancellationSubmissions` and `canSaveCancellation`; the compatibility `hasCancellationSubmission` flag still means any cancellation exists. These are submission capabilities and report summaries, not a generic flight status.

## Flight services

The accepted service and task business rules on `main` remain the baseline for this redesign; see the [source baseline](https://github.com/houranigit/NAGS.OperationSystem/tree/da351660897f7845fd70e1f191bd5e0f22346939/src/Modules/Operations/Operations.Domain). The agreed changes are direct flight ownership, open work windows, stable child corrections, and task/performer notes. A change in ownership or application workflow does not by itself remove an existing resource rule.

`Flight.Services` exposes normal actual `FlightService` records separately from `PlannedServices` and return-to-ramp work. The mapped `ServiceRecords` collection contains both normal and return-to-ramp services. Each records a service snapshot, a `TimeWindow`, optional customer reference number, and optional notes. Optional text is trimmed and becomes null when blank; customer references are limited to 200 characters and notes to 2,000. Unknown services require notes, and Aircraft Per Landing cannot be recorded as an actual service. A window has a required UTC start and an optional UTC end; a supplied end must be at or after the start. Repeated occurrences of the same service are allowed.

`TimeWindow` contains only the start and end instants and is also used by employee work periods. On the service, `CreatedByUserId` is the single source of truth for the starter, since adding the service starts it; there is no separate starter field. `EndedByUserId` is null for an open window. Supplying or correcting the end time records the acting user; clearing the end clears that identity. An initially closed service records its creator as both starter and closer. Changes that keep the same end time, including notes, performer, or attachment edits, preserve the closer. The closer is a recording-user identity, separate from the employees performing the service and the user who last edited it.

Each service owns at most one performer record per employee, containing an employee snapshot and that employee's own time window. Employee periods must start at or after the service start; when a service end is supplied, neither the employee start nor a supplied employee end may exceed it. Parent-window corrections revalidate existing periods. Services, performers, and attachments have stable identities. Parent-scoped updates preserve other records and attachments; removing a performer or attachment affects only that record. Service records and attachments retain actor and timestamp metadata. Services have no acceptance flag or per-employee submission selection; review remains a later workflow. This slice adds no schedule bounds or accepted-arrival prerequisite.

Each service or task allows at most ten attachment entities. `AttachmentDetails` requires an explicit `Kind` (`Image = 0`, `Voice = 1`, `Document = 2`), file name, storage key, content type, and positive byte size. File names are reduced to the basename and truncated to 255 characters; storage keys are limited to 500 characters and content types to 100. Attachment records retain their parent, uploading user, and timestamp. Bytes belong in file storage through the existing `IFileStorage` boundary. Domain attachment records contain metadata only. The Service and Task workflows below supply byte transfer, scoped reads, and file policies.

### Service saving and local drafts

`main` remains the behavior reference for service defaults, eligibility, validation, and media handling. Opening the form seeds allowed planned services that have not already been recorded, excluding Aircraft Per Landing. New service rows include the logged-in employee in Performed By. Planned rows start without a service start time; setting their first start initializes any blank default staff starts. Unstarted rows, their media, intentionally removed planned-service choices, and task editor values are durable account/API-scoped local form drafts. Only started work becomes operational upload requests. Tasks use their own queue and API below, retaining their existing draft files until that queue imports them.

Every started service save requires at least one unique staff performer, as on `main`. Active service choices retain the caller's manpower-type eligibility; mobile details cache the caller's `allowedServiceIds` separately from the general reference catalog. Service and staff periods retain `main`'s bounds against actual ATA/ATD when available, using the same own/accepted/earliest submission selection as the form. Changing ATA/ATD also revalidates retained normal service/staff periods; correcting other actual-record fields without changing the actual instant does not introduce a new bound. No scheduled-time bounds or accepted-arrival prerequisite is added. The deliberate open-work improvement keeps service and staff ends optional while work is in progress. Supplying service End requires every staff period to have End; both the form and API reject closing a service with open staff periods. Saving departure requires all recorded normal service and staff periods to be closed; unstarted local drafts do not participate. Once a visible actual departure exists, a changed service save must close that service and its staff periods, without blocking repairs because some other service remains incomplete. Deletes and exact retries retain their existing rules. New or replaced performers must be active at the flight's station. An unchanged stable performer ID and staff ID retain their captured snapshot after a later staff move or deactivation; this permits authorized corrections or End-only closing without changing historical attribution or widening edit ownership. An employee assigned to the flight may correct or delete another employee’s normal Service, including active or completed work, through the existing scoped routes. Full corrections include the selected service, core fields, staff periods, remarks, attachments and End. Original record ID, creator and creation time remain intact. An unchanged End retains its closer; changing or clearing End updates that attribution as described above. The domain checks assignment before granting this correction/deletion capability. For eligible nonassigned callers, existing creator/closer restrictions and End-only contribution behavior remain. Existing cancellation, catalog, period, attachment and concurrency guards still apply.

`PUT /api/v1/operations/flights/{id}/services/{recordId}` and `DELETE` on that same route require `operations.flights.operate`, the existing mobile scope, and an eight-byte `If-Match` rowversion. Service and performer IDs remain stable through corrections; separate identical service occurrences use different IDs. Exact normalized retries acknowledge the same record without another write or file upload, recovering a lost success response. Changed stale input remains a reviewable conflict. Responses carry the saved service or removed ID, flight rowversion, and authoritative active/completed work counts. Normal service changes preserve other services and RTR work.

Attachments retain `main`'s ten-per-service limit and byte/type checks: PNG, JPEG, and WebP images up to 10 MiB, supported audio up to 25 MiB, PDFs up to 2 MiB, and at most 25 MiB of inline file content per service request. The existing file-storage boundary owns bytes and server-generated storage keys. Retained attachment IDs are immutable; replacement files receive new IDs. Scoped versioned downloads require flight-view access, return private/no-store responses, and expose no storage keys. Cleanup checks references before removing files after failed or ambiguous saves/deletes.

Room versions 8–9 add service intent and local form-draft storage without replacing earlier queues or caches. The version-9 migration supports both intermediate and completed version-8 layouts, adding only missing arrival review columns and the form-draft table. Save copies selected/captured media into durable private storage before the atomic local write succeeds and the form closes. Pending input remains editable offline. Desired input/files are separate from any transmitted request/files awaiting acknowledgment; retries retain that exact attempt. The existing session/reconnect/foreground/manual/background drain resolves older frozen requests first. New Saves use the combined atomic boundary below, including coordinated actual-time and work corrections. Cancellation retains its separate guarded queue. Only acknowledgments of this account's own writes advance dependent versions, with reviewed-service comparisons when needed; external changes never cause a silent rebase. Sync Center retains unresolved started-service changes for review, retry, or safe local discard. Unstarted form drafts are not represented as pending online publication. Account transitions wait for active sends and clear both queues and draft/media ownership.

## Flight tasks

`Flight.Tasks` exposes normal `FlightTask` records; the mapped `TaskRecords` collection contains both normal and return-to-ramp tasks. Each task has a required `TaskType` (`Major` or `Minor`), a `TimeWindow`, optional ATA chapter snapshot, optional customer reference number, and optional notes. ATA chapter snapshots contain the chapter ID, code, and title. MasterData retains catalog ownership; these snapshots add no cross-module foreign keys. Optional text is trimmed and becomes null when blank; customer references are limited to 200 characters and notes to 2,000.

Each task owns tool, material, general-support, and performer records with optional notes of at most 2,000 characters. A resource ID may appear only once per resource collection on a task, and an employee may appear only once per task. Unknown tool, material, or general-support selections require notes. Tasks and all their children have stable identities, and updates or removals are scoped to the owning task.

Resource snapshots preserve their catalog `CalculationType`: `Quantity = 0` or `Duration = 1`. Tools default to Duration; materials and general supports default to Quantity. `ResourceUsage` must match that snapshot and contain exactly one branch. Quantity usage requires a positive value fitting `decimal(18,2)` (at most `9999999999999999.99`) and forbids both duration times. Duration usage forbids quantity, requires a valid UTC start, and allows an optional valid UTC end at or after the start. SQL check constraints retain the same branch and snapshot-type agreement.

Resource duration windows and employee periods must start at or after the task start. A supplied child end cannot exceed a supplied task end; employee starts also cannot exceed a supplied task end. Employee periods use `TimeWindow`; resource periods use `ResourceUsage`. Parent-window corrections revalidate all existing periods. Open task windows have no upper end bound until an end is supplied. No schedule-bound policy is added.

As with services, `CreatedByUserId` is the sole starter identity. `EndedByUserId` is null while the task window is open; initially closed tasks use the creator as closer. Supplying or correcting the end records the acting user, clearing the end clears the closer, and other edits preserve it. Attachments use the existing `AttachmentDetails` file metadata and upload actor/timestamp fields; file bytes remain outside the relational model. Tasks have no acceptance flag or per-employee submission selection.

Task saving does not calculate prices, consume stock, or bill resources. The scoped workflow below adds publication and file transfer; approval selection remains deferred.

### Task saving and local drafts

The Task form retains `main` defaults and validation: Major by default, the current station employee in Performed By, at least one unique station performer for Major and Minor, optional active ATA chapter, 200-character customer reference, and 2,000-character optional remarks on the Task and its staff/resources. Unknown resource choices require remarks. Saved unchanged staff, chapter, and resource snapshots remain usable after reference deactivation or changes; new selections must be active, with staff at the flight station.

Resource calculation type comes from the catalog or retained snapshot. New Quantity choices show an editable quantity of 1; values use precise decimal strings over JSON and must fit the existing positive `decimal(18,2)` contract. Duration choices retain their separate periods. An older local quantity-resource draft with time values keeps those values visible and requires a deliberate valid quantity edit before replacing that branch. No old draft times are silently converted to quantity. `main`'s resource containment rule remains: duration Start is at or after Task Start, while a supplied resource End cannot exceed a supplied Task End. Task and staff periods also retain the actual ATA/ATD bounds when available.

Task and nested period Ends may remain blank during ongoing work. For normal flight Tasks, the explicit improvement over `main` requires every staff and Duration-resource End before supplying Task End; existing return-to-ramp rules remain unchanged. Quantity resources have no period to close. Departure requires complete periods on recorded/queued started Tasks, while unstarted local drafts do not block departure. After a visible actual departure, changed Task saves must be complete too; deletion and identical retry acknowledgments retain their existing semantics.

Assigned employees may correct or delete another employee’s normal Task, active or completed, including its type, staff, resources, remarks, attachments and End. The original record identity, creator and creation time remain intact; unchanged End retains its closer. Other eligible nonassigned employees retain the existing creator/closer restrictions and End-only contribution behavior. During explicit conflict review, a local End that was not edited follows the latest recorded End, including an external clear; a deliberately changed local End is retained when the current capability permits it. An incapable conflicting End still requires the explicit Keep recorded End choice.

`PUT /api/v1/operations/flights/{id}/tasks/{recordId}` and `DELETE` on the same route require `operations.flights.operate`, the current eight-byte `If-Match` rowversion, and the existing mobile station/category/window boundary. Task, staff, resource, and attachment identities remain stable through updates. Atomic child reconciliation preserves unchanged identities and snapshots; normal work never mutates RTR records. Exact normalized retries acknowledge prior success without another write or upload; changed stale requests remain reviewable conflicts. Scoped versioned attachment downloads use the same file policy as Services and expose no storage keys.

Room version 10 adds Task intent without replacing existing queues, caches, or form drafts. The account/API-scoped Task queue stores desired input/files separately from frozen transmitted attempts. Old Task draft media is imported durably before shared-draft cleanup. Reopening pending Tasks permits offline corrections; acknowledgment caches previews before releasing queue files. Fresh work waits for unknown sibling attempts. New Saves publish actuals and work through the combined atomic boundary below; only known own acknowledgments advance waiting versions. Sync Center provides Task review, retry, and safe local discard; account transitions retain the existing send/session guards. Unstarted and unchanged pre-feature local Task drafts remain in the combined form draft until explicitly changed or removed.

Both Services and Tasks show saved or queued operational records as compact read-only cards. The left side holds the service name or task number/type, Active/Done state and optional customer reference/ATA chapter; the right side keeps equal Start → End clock columns and the station-local date. Large text may move the right-aligned timing block below the identity. View details expands indented staff/resources with their own periods or quantity, optional remarks and existing media viewing/playback. The original submission note sits outside the card, with creator and timestamp in semibold, followed by Update Service… or Update Task…; 28dp separates that note from the next card. Creator/closer display names come from one bounded Identity lookup and never from the performers. Missing historical names are omitted without inventing an author.

Update opens a record-specific prefilled page. Its Save or permitted minus/reveal-Delete operation edits only that stable record, retaining all other open drafts. It joins any pending combined Save for the flight without dropping the other saved sections. Delete remains pending inside the editor until Save; Back/discard restores the parent unchanged. New entries use the existing immediate Service/staff/resource pickers and inline Task slider, with Draft captions; canceled pickers create no rows. Queued additions are captioned Saved on this device using the queue save time; queued corrections retain original attribution. Read-only rows reconcile cache/queue changes independently of unrelated dirty local drafts, without adopting external rowversions. Media ownership, actual-time bounds, full-period validation, frozen retries and account guards remain in force.

## Return to ramp

`Flight.ReturnToRamps` owns `FlightReturnToRamp` occurrences. Starting one requires any flight departure submission, including an unaccepted submission; it does not require an approval selection. A flight may have only one open occurrence. Each occurrence has one required `RtrArrivalDetails` value object and one optional `RtrDepartureDetails` value object, rather than per-employee submission lists. Arrival requires a UTC time and receiving employee; departure requires a UTC time and handling employee. Remarks on either record are optional, trimmed, and limited to 2,000 characters.

Departure closes the occurrence and cannot precede its arrival. There is no additional comparison with a flight departure time or another occurrence's times. The occurrence's stable `Sequence` comes from the persisted `LastReturnToRampSequence` counter, is retained on corrections, and is never reused after removal. Creation and edit actors/timestamps are retained, and `EndedByUserId` records who supplies or corrects its departure.

Return-to-ramp services and tasks reuse the existing work models and all retained service/resource rules. Each has an immutable optional `ReturnToRampId`; null identifies normal work. Occurrence activity windows must stay within its arrival/departure window. Closing requires at least one service or task, a closed window and at least one performer on every service/task, and closed employee periods. Resource usage retains its Quantity/Duration rules, including optional duration ends. Valid corrections to closed occurrences are allowed, but arrival, departure, and child changes validate retained work before mutation. Closing does not introduce a new approval or authorization workflow.

The departure signature is optional and uses the same `CustomerSignature` value object as normal departure. When supplied, all five fields are validated: `FileName`, `StorageKey`, `ContentType`, positive `SizeBytes`, and required UTC `SignedAtUtc`. The same basename normalization and 255/500/100-character limits apply, and the value is copied independently into its owning departure record. The optional signature and optional RTR departure remain absent when not recorded; shared signature validation does not make either mandatory. These are metadata references to the existing file-storage boundary, without upload, download, physical deletion, or signing UI.

## Operational persistence boundary

Domain guards use loaded collections. Write callers must load all three submission collections, all `ServiceRecords` with performers/attachments, all `TaskRecords` with tools/materials/general supports/performers/attachments, and `ReturnToRamps` with their work graph. The public `Services` and `Tasks` views are not mapped navigations and exclude occurrence work. For an existing tracked flight, changes anywhere in these attached graphs, including nested edits or removals, force the flight's rowversion check in synchronous and asynchronous saves, even when `UpdatedAtUtc` is unchanged. Return-to-ramp sequence uniqueness and the single-open-occurrence rule are also indexed in SQL. Composite occurrence/flight foreign keys prevent work from being grouped under another flight's occurrence. Flight remains the cascade-delete path; occurrence relations use `NoAction` to avoid multiple cascade paths. There is no database constraint enforcing cancellation exclusivity across tables, so direct SQL bypasses it. Arrival, departure, services, and cancellation retain rejected/conflicting device intent for the explicit reload/review workflows above. Return-to-ramp operational conflict workflows remain deferred.

Arrival and departure add their API/mobile queues described above. Services and Tasks add the scoped save/delete, attachment transfer, and local draft/queue workflows above. Return-to-ramp application workflows, approval selection, portal operational writes, and billing remain deferred. Flight detail reads include arrival and departure submissions alongside planning details. Persisted lifecycle statuses, approval, further prerequisites, and chronology policies remain for the later workflow discussion; the mobile card summaries below add no stored workflow state.

### Combined operational saves

The mobile flight form and record-specific editors publish saved Arrival, Departure, Service and Task changes through `PUT /api/v1/operations/flights/{id}/operations-batch`. The request contains optional `arrival` and `departure` values plus `serviceChanges` and `taskChanges`; each work change identifies a stable `recordId`, with null `input` deleting that exact record. One reviewed `If-Match` version covers the whole request. The response is the final scoped flight detail. Existing single-record routes remain available for older clients and previously transmitted queue attempts; cancellation stays a separate workflow.

The batch validates request fields, catalog eligibility, permissions, media bytes and the resulting work periods before one database save. Operational records, audit and notification outbox changes commit together. A rejected or stale batch publishes none of its changes. New files are staged privately, replaced files are retained until commit, and reference-safe cleanup follows the outcome; this is not a filesystem transaction. A complete exact retry can acknowledge the already saved batch without writing again. A stale retry with any differing member requires review of the whole saved intent.

Per-record attachment and signature limits remain in force. A batch additionally permits at most 100 MiB of new inline file content, with a 150 MiB encoded request-body ceiling. Oversized saves are rejected as a whole and never split into independently published requests.

Android commits the combined local intent and form draft in one Room transaction, retaining all editor values after a validation or storage failure. Its durable batch is uploaded as one request; grouped queue projections cannot drain through separate section endpoints. Frozen requests keep their reviewed version and exact transmitted input through retries. A later server rejection retains the whole batch for review. Retry and permitted Discard apply to the entire saved batch; an unknown server outcome must be acknowledged before it can be discarded. Unstarted planned work remains a local draft rather than an incomplete operational submission.

Room version 11 adds the durable batch table without replacing existing queues or caches. Version 12 upgrades both intermediate and completed version-11 layouts, adding only missing batch comparison/rejection flags with zero defaults while preserving rows, frozen attempts, existing flag values and file references. Version 13 also repairs intermediate version-12 variants and adds nullable review-source snapshots to the four section queues without rewriting their existing input. Before any individual queue drain, unsent older-client intent is grouped by flight and checked as a whole. Different reviewed versions or unavailable media hold the group for review rather than publishing a prefix. Previously transmitted individual requests retain their exact replay path; additional unsent work waits while an existing whole-batch outcome is unknown. No upgrade or Retry adopts a freshly fetched flight version as its reviewed base.

### Reviewing rejected operational input

A rejected Arrival, Departure, Service or Task marks its flight **Needs review**. In the flight form, that notice opens the first unresolved section in Arrival/Services/Tasks/Departure order; the failed entry offers a red **Review…** link instead of Update. Update and Review reuse the same record editor. Review starts with current online fields and a separate **Your saved input** card below. Opening it does not replace or discard local intent. Offline Review explicitly identifies the last downloaded online snapshot and retains its reviewed version; reconnect does not silently adopt a newer version.

**Discard** removes only that card's safe local intent and retains online records and other saved sections. **Overwrite** stages locally provided values into the editor without publishing. Blank or absent local text, missing optional times/signatures and empty local collections retain the online value. Populated staff/resource collections merge by stable or semantic identity, preserving online child IDs; new attachment IDs are added without replacing immutable published attachments. An explicit saved work deletion remains a deletion intent. Users can edit the resulting fields before Save. **Submit Anyway** is visible but disabled; duplicate-conflict creation, administrator resolution and the third colleague's conflict view are not part of this workflow.

The queues persist a sparse review source separately from the full desired request. Values inherited from online input stay absent from that source across another rejection, process recreation and later edits; explicit manual edits become local values. Signature bytes remain private files, not large JSON or saved-instance-state values. Review Save checks the exact local card identity and current ownership, validates and commits the replacement atomically. Reviewing one member of a rejected combined Save holds the entire group until every remaining member has been reviewed or discarded against a common version. Another server rejection publishes none of the group and returns it to review. An unknown transmitted outcome must resolve through exact replay before Review can replace or discard its intent.

## Scheduling and validation

The existing flight grid and scheduling dialog support a single flight, multiple selected dates, and basic schedule edits. Required fields are customer, station, operation type, flight number, arrival/departure, and at least one planned service. Aircraft type and assigned staff remain optional. Staff assignments require the existing assignment permission and active staff at the selected station.

The scheduling input shows the customer code as a separate prefix. Flight numbers accept 1–4 digits, optionally followed by either one letter or `/` and one or two route digits; a letter and a route cannot be combined. The dialog checks this format and required details locally on the first Next click. The customer's IATA code may be entered or omitted; it is never required in the input. The backend adds it when missing, validates the complete number, and normalizes letter case on single creation, batch creation, and number changes. For customer `SV`, `123A` or `SV123A` stores `SV123A`, while `123/01` or `SV123/01` stores `SV123/01`. Whitespace, dashes, additional letters, more than four flight digits, empty routes, and routes longer than two digits are rejected. The 12-character storage limit remains, and the grid displays the saved number directly. Existing stored numbers are not rewritten, and planning-only edits preserve them. Number changes use the customer's saved snapshot IATA code.

Aircraft Per Landing remains an exclusive planned designation and cannot be combined with other planned services or assigned staff. Ad Hoc is unavailable for scheduling. All operational date/time inputs in web and Android use the station’s configured IANA `TimeZoneId`, including scheduling and service/task/resource periods. Flight schedules and operational times are displayed in that same station zone without time-zone captions. UTC instants remain the storage and API contract. Recurring scheduling resolves the current station zone on the server for each selected date and preserves overnight departures; any legacy request `TimeZoneId` is ignored. Invalid or ambiguous local times fail validation rather than silently shifting the schedule. Station time zones are mandatory. The migration supplies `Etc/UTC` as a generic value for existing rows; administrators must replace that placeholder with the airport’s correct zone before entering local operational times. Station and flight contracts require valid zone metadata; clients use the station clock directly without configuration prompts. Older cached flight details missing required metadata follow the existing refresh policy. Flight read responses expose the current station zone, and mobile caches it with the flight for offline operation; a station-zone change refreshes flight metadata. Audit and notification metadata retain their existing presentation rules.

## User notifications

A changed Arrival/Departure correction or Service/Task update/deletion by an assigned non-submitter enqueues `FlightSubmissionUpdated` with the Operations save. Notifications consumes it through the existing inbox/outbox boundaries and creates a blue informational Flight Updates item for the original submitting user, identifying the updater, section and flight. The existing contract adds Service/Task kinds and an action that defaults to Updated for old envelopes; deletion messages use Deleted. Service/Task notifications address the stored original creator account. Creation, own edits, no-ops, exact retries and rejected changes do not create colleague-change notifications. The original submitting user ID is retained rather than resolving a later staff-account relink. Exact retries, unchanged input and rejected corrections do not enqueue another update; the notification consumer deduplicates event delivery by its existing inbox identity. Its View action opens the flight under the normal current mobile access rules.

Scheduling one flight with assigned staff, adding employees through roster replacement or the planning editor, and inviting employees queue transactional `FlightEmployeeAssigned` events for newly added employees only. Invitations use `EmployeeInvitedToFlight`; other additions use `StaffAssignedToFlight`. Repeated selections and removals are silent. A batch that creates multiple flights queues one `FlightScheduleUpdated` event per distinct assigned employee instead of one notification per flight; a batch with one distinct date uses the single-flight assignment behavior. Editing flight times alone does not produce a schedule-update notification.

Notifications resolves the employee's linked user, suppresses assignment/bulk self-notifications and unlinked recipients, saves bilingual inbox entries, and attempts the existing SignalR/FCM transports. Transport retries reuse the event/notification ID and do not reverse an accepted flight change.

Mobile and portal present an English-only, single notification feed: **New** first, then older entries grouped by local date. New entries keep their background tint during the current visit. Opening the inbox acknowledges all kinds through the newest observed creation timestamp; newer entries remain unread until observed. Cached history and pending read cutoffs survive reconnects. Cards append a bold short relative age to the message and use distinct kind colors. Only the explicit card action navigates. Mobile labels it **View** and shows it solely when the notification flight reference is present in the local **My Flights** tab; it adds no notification-kind or reminder-age gate and makes no availability API or pre-open validation request. The portal retains Operations availability checks in batches of at most 100 IDs under its existing flight-read scope and rechecks before navigation. The normal detail loader retains its access checks and mobile offline saved-detail requirements. A partial left swipe reveals compact red **Delete**; a full swipe invokes the same archive operation automatically. Failures restore the row and successful removal animates. Paging is automatic and notification rows are virtualized.

Flight reminders retain `main`'s durable 12-hour, 2-hour, and 30-minute milestones before STA. `Operations:FlightReminders` enables the scanner by default, polling every 60 seconds with a 13-hour enrollment horizon and five-minute enrollment lateness tolerance. Milestones already too old at enrollment are skipped. Dispatch skips superseded milestones, removed assignments, missing flights, changed STA snapshots, and expired STA. Notifications rechecks live eligibility before persistence, delivery, and transport retries.

This model has no terminal flight status. Any cancellation submission, including competing unaccepted submissions, suppresses reminder enrollment and delivery, independently of which employee submitted it and whether an opposing arrival/departure report also exists. Arrival and departure submissions do not introduce a completion status. Reminder schedules belong to Operations; inbox entries and device delivery remain owned by Notifications. Reminder scanning and transactional outbox dispatch must both be enabled for delivery.

Existing staff roles must be granted `operations.flights.operate` explicitly; arrival saving does not reuse planning-update permission. Existing account/station scope remains enforced on the backend. Viewer accounts are read-only; station staff see assigned flights and station-wide Per Landing flights unless granted station-wide visibility. Customer contacts have no Operations access.

## Database change

Submission, performed-service, task, and return-to-ramp storage uses additive Operations migrations that preserve existing flight planning and operational data and do not change another module's schema. Cancellation adds an initially empty `operations.flight_cancellation_submissions` table. Performed services add Operations tables for service records, performer periods, and attachment metadata. Tasks add Operations tables for task records, tool/material/general-support usage, performer periods, and attachment metadata. Return to ramp adds an occurrence table, a flight sequence counter, and nullable occurrence ownership on existing service/task rows; existing work remains normal work with no occurrence ID. Generating these migrations does not apply them to configured databases. The task migration also restores the service text/attachment limits and employee uniqueness. It checks existing service data before narrowing columns or adding indexes, and stops with a diagnostic if records violate restored rules. It preserves existing IDs, storage keys, and actor/timestamp metadata; existing attachment display names are normalized and attachment kinds are derived from their MIME types. It does not delete conflicting records or truncate notes, references, or storage keys.

The shared-signature migration is additive after the published migrations and adds required `CustomerSignatureFileName` and `CustomerSignedAtUtc` columns to normal flight departure submissions. For those legacy normal-departure rows only, the file name is derived from the existing storage key basename (normalizing both slash styles), truncated to 255 characters, and set to `customer-signature` when the basename is empty. `CustomerSignedAtUtc` is backfilled from the submission's `CreatedAtUtc`: this is a documented historical fallback to recording time, not a claim about the actual signing time. Preflight stops on legacy keys over 500 characters, content types over 100 characters, or a default submission creation time, rather than changing file references or fabricating a time. Existing RTR signature metadata is already complete and remains untouched.

Keep the historical `main` EF migrations unchanged. `Operations_FlightSchedulingBaseline` preserves the existing flights, direct `flight_planned_services`, and `flight_assigned_employees` rows in place, and removes retired work-order, mobile, reminder, history, status, contract, and merge storage plus pending event envelopes for retired Operations contracts. The retained `FlightEmployeeAssigned` invitation contract and platform audit envelopes are preserved. The migration does not require a HandOver operational graph. It does not alter another module's schema or delete stored file blobs.

`Operations_RestoreFlightNotifications` subsequently recreates Operations-owned durable reminder schedules with unique flight/employee/STA/milestone identities and dispatch/cleanup indexes. Existing flight, roster, submission, and notification data is preserved. Historical reminder rows removed by the scheduling baseline are not replayed; the scanner enrolls currently eligible assignments.

This migration intentionally discards work-order/workflow data. Development startup migrations are disabled. Review the SQL and back up an existing database before applying the reset and running the API against that database. Restoring the previous application requires restoring its database backup; the reset migration cannot reconstruct the removed operational history. Verification uses disposable local SQL databases, never a configured remote database.

The isolated current-branch Docker target is `OperationsSystemOperationModuleMain`, initialized from a main-compatible database copy. The earlier HandOver-derived `OperationsSystemOperationModule` database remains preserved under its original name and is not overwritten or reused for this migration chain. Main/release remains a separate stable environment; see the [local environment runbook](../architecture/production-runbook.md#concurrent-local-environments).
