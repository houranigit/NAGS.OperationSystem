# NAGS Operations — Android

The native Kotlin/Compose client supports the current [flight baseline](../../../docs/modules/operations-foundation.md): view flights, open basic planning details, invite employees, save arrival details locally and online, save departure details locally and online with a customer signature, save and revert cancellation locally and online, and synchronize shared MasterData catalogs. Flight creation, single/batch scheduling, and planning edits remain in the web portal.

## Departure saving

Departure Save works offline with the last successfully read flight eligibility and `operations.flights.operate` capability. ATD and a customer signature are required for the first submission. Save stores the normalized input, UTC signing time, reviewed version, and private PNG signature bytes before closing the form. The queue belongs to the current account and API; it is separate from replaceable flight snapshots. Room version 6 adds the departure queue without changing existing arrival input. Signature bytes use durable private files rather than large base64 values in database rows. Reopening pending input restores ATD, remarks, and the saved signature; correcting it without drawing a replacement retains that signature. Clearing an unsaved ATD removes that input; it does not delete an existing departure record.

`PUT /api/v1/operations/flights/{id}/departure` retains the same mobile flight eligibility and server validation. Upload resumes on reconnect, session/foreground/manual refresh, and network-constrained background work. It waits for any saved arrival input on that flight to be acknowledged first. Only acknowledgments of this account’s own arrival input may advance the departure’s reviewed version; a live departure comparison guards an advanced version without adopting a version from that read. A transmitted departure request, its signature, and its version remain separate from newer desired edits until acknowledged, including across process restart or a lost response. An identical retry can recover an accepted save without storing a second signature; its acknowledgement then advances any newer correction.

Transport failures retain pending input for retry. Conflicts, rejected input, and access loss retain it for explicit reload/review rather than automatically overwriting current server data. Sync Center exposes retry and confirmed local discard. The server attributes submission and handling to the authenticated linked staff member; another employee’s saved departure remains read-only. An owner correcting a departure may keep its server signature by omitting replacement signature content. Services and tasks stay temporary.

## Cancellation saving and reversion

Cancel Flight is hidden when the current employee has a saved arrival or departure, including durable local input. Their own saved or queued cancellation hides Open Flight and offers Revert cancellation. Another employee's report does not silently decide the current employee's report. Before cancellation Save, existing arrival/departure reports from other employees require confirmation; before arrival/departure Save, another employee's cancellation requires confirmation. The acknowledged warning is retained with the queued request. A report that appears after the last read can still fail server validation and require review. Both the local save boundary and server reject one employee holding cancellation and work submissions on the same flight.

Cancellation contains a required station-local date/time and optional remarks. Save writes the UTC input to the account/API-scoped cancellation queue before closing the form; connection recovery uses the same foreground, refresh, and WorkManager drain as arrival/departure. Room version 7 adds `flight_cancellation_pending` without changing existing arrival/departure rows or signature files. A shared local submission gate prevents work and cancellation saves racing into separate queues. Pending cancellation reversion continues to block work until the server acknowledges it.

Revert cancellation removes only the current employee's report. Reverting an unsent cancellation removes its local intent; a cancellation with an unacknowledged transmitted save must first recover that exact save, then revert its exact submission ID. Confirmed reversion can itself wait offline. The server uses `PUT /api/v1/operations/flights/{id}/cancellation` and `DELETE /api/v1/operations/flights/{id}/cancellation/{submissionId}`, with `operations.flights.operate`, the current `If-Match` rowversion, and the same mobile scope as other operational writes. Unchanged lost-response retries can acknowledge an existing save or completed revert. Conflicts remain reviewable in Sync Center. A transmitted pending cancellation cannot be discarded as if it had never reached the server; use Revert cancellation. Other employees' reports, planning, and service/task/RTR rules are preserved.

## Flight synchronization

Normal list responses carry `hasArrivalSubmission`, `hasDepartureSubmission`, and `hasCancellationSubmission` flags; reports count regardless of employee or acceptance. Additive read fields `hasOpenReturnToRamp`, `latestReturnToRampSequence`, `activeWorkCount`, `completedWorkCount`, and `latestCancellationAtUtc` supply card summaries from existing records. Counts include both services and tasks, using the latest existing RTR by sequence when any remains, otherwise normal work; an absent end counts as active and a recorded end counts as done. The cancellation time is the latest reported cancellation instant, not an approval selection. The server projects these scalar values within the existing paged station/category/window scope, without a detail request for each card. Android retains the additive fields in the existing JSON cache payloads without a Room migration or new schema. Missing counts and RTR metadata in older snapshots remain unknown; they are not converted to known zero or false. Missing report flags can use already-cached eligible detail evidence; absent evidence keeps Scheduled rather than inferring a missing arrival from STA. Acknowledged saves update scoped snapshot flags and confirmed cancellation times before their queue rows are released, preserving work/RTR summaries. A saved or possibly transmitted cancellation stays represented while its exact reversion awaits acknowledgment; reverting an unsent local cancellation restores the prior badge immediately.

The **Flights** card in Sync Center reports the cached scoped register's count, last successful refresh, duration, and errors. Synchronization reads only the eligible union of the three categories from `/api/v1/operations/flights/mobile`. It never downloads the unrestricted portal register. Each page includes its server station/window metadata; the server recomputes the window for each request. Details opened online are cached only when their flight is in the complete bounded snapshot; a live detail opened before the first successful sync is not an offline orphan. Full flight refreshes revalidate previously cached details and remove flights no longer returned or accessible. Flights never opened online require a connection to load their details. Offline flight paging filters the last successful bounded snapshot by the requested category and the current rolling window, and the screen identifies cached data. Visible cards and open details expire as the window moves, including while offline. Legacy unrestricted flight snapshots and orphan details are discarded before fallback; shared reference catalogs remain intact.

A successful schedule, planning edit, number change, roster change, or invitation addition publishes a best-effort flight refresh hint. Flight hints refresh flights only and refresh an open flight view; catalog hints remain catalog-only. Background detail refreshes keep the current flight and its actions visible, updating them in place after success. Initial loads still use placeholders, transient refresh errors retain the details with a retry message, and access loss or expiry still removes unavailable content. Staff station/active changes and station active changes also invalidate flights because they can change the caller's visibility. Full sign-in/token, foreground, reconnect, periodic, and **Refresh now** checks cover both flights and the eight reference catalogs. A failed connection retains the last successful flight snapshot unless valid page metadata confirms a changed station: the previous station’s rows, details, and logo authorization are removed immediately, even if later pages fail. An authorization denial evicts denied flight data. Offline access reflects the last successful authorization check and cannot observe server access changes until reconnecting. Account/server ownership and session-generation guards prevent another session's cache or late replies from being reused.

## Shared catalog synchronization

The app caches eight shared reference catalogs: customers, aircraft types, services, tools, materials, general supports, ATA chapters, and station staff. `SharedCatalogsApi` reads their existing `/api/v1/masterdata/{catalog}/options` endpoints through the same authenticated API client and configured branch URL as flight requests. These are active lookup records, not work-order forms or personalized performed-service allowances.

Each endpoint requires `masterdata.reference.view-options` or its catalog's `.view` permission. Flight viewing does not grant catalog access. Administrators, station staff, and Viewers use their configured grants; a Customer Contact with customer-view permission can receive only their own customer options. Synchronization does not broaden those scopes or add permissions. Station staff use the existing `/api/v1/masterdata/staff-members/options` route: station-staff accounts receive only active members of their own station, global readers retain their existing scope, and customer contacts have no staff access. The **Station staff** cache and status card are separate from the flight-specific invitation options, which remain live and enforce invitation eligibility.

Customer options include an opaque `logoVersion`; `none` means the customer has no logo, while a missing/null version is older or unknown metadata. The scoped flight register supplies `customerLogoVersion` for customers visible through Operations, including accounts without customer-catalog access. One account/API-scoped logo store reconciles these versions and saves images on demand under the app's private no-backup directory, outside the Room catalog payload. Unchanged versions reuse the existing file; a changed version replaces only that image after a successful download, and `none` removes only that customer's image. Failed downloads retain a previous good file for retry. Signing out, changing accounts, or losing flight access removes the affected saved images. The full scoped flight register governs visibility cleanup; a denied customer catalog does not remove logos still authorized through flights.

Open **Sync Center** from the Sync Center action in **My profile**. The restored page shows network online/offline status, live-channel connection state, the last accepted catalog event, and each catalog's cached count, last successful refresh, measured duration, and current error or permission denial. **Refresh now** refreshes all eight catalogs and flights. Connection status is independent of cache freshness: a connected channel can be awaiting its first event, and a failed channel does not stop HTTP refreshes. The last accepted event remains visible while offline and clears when the session ends. Full refreshes also run after sign-in/token refresh, reconnecting to the network or catalog hub, returning to the app, and every five minutes while the app process is active and connected. A live catalog-change hint refreshes only the affected catalog; ordinary staff changes refresh the staff cache without changing other catalogs' sync metadata. Staff/station access changes also trigger flight revalidation. **Last sync** records the last successful fetch, rather than the last data change: another catalog's event leaves that timestamp unchanged, while a full refresh updates it for every successful fetch. Creating a record, changing active lookup fields, or activating/deactivating a record publishes a refresh hint after persistence succeeds. Deactivation therefore removes it from the next cached active-options snapshot. Customer logo replacements also publish customer hints, including for inactive customers; byte-identical uploads keep the existing file/version and publish no hint. Other changes outside the lookup payload, inactive-only edits, repeated state transitions, and rejected writes do not publish hints. Hints are best-effort; periodic and foreground refreshes also cover missed delivery. No background WorkManager catalog job is installed.

`CatalogDatabase` version 7 stores catalog snapshots, independent arrival/departure/cancellation queues, and separate flight-register/detail tables keyed by API base URL and authenticated account in `shared-catalogs.db`, separately from the notification cache and unopened legacy database. Copied account IDs in the main, HandOver, and Operation Module APIs cannot expose another environment's cached catalog snapshot. The explicit version 1 → 2 migration preserves existing catalog snapshots and adds duration metadata; version 2 → 3 adds flight tables without replacing those snapshots. Versions 3 → 5 add arrival intent and its immutable transmitted snapshot, version 5 → 6 adds departure intent with private signature-file references, and version 6 → 7 adds cancellation save/revert intent. These additive migrations preserve existing caches and queued input. A network or parsing failure retains the last successful catalog snapshot and its timestamp. A `403` clears that catalog's cached records and records the denial; `401` clears the catalog cache. Signing out or changing accounts clears shared catalog snapshots. Catalog permissions do not grant flight access. Flight caching uses only the scoped Operations API; invitation eligibility and writes continue to require that API online.

## Identity and Notifications

Existing email/password sign-in, enrolled TOTP MFA, secure bearer/refresh-token storage, session refresh, basic profile, and sign-out remain. Native authentication uses `/api/v1/identity/auth/mobile/*`; profile uses `/api/v1/identity/me`.

The English-only notification inbox retains its cached history, unread bell count, and configured FCM registration. Inbox **View** buttons use one visibility rule: the notification flight reference is present in the current account’s locally synced **My Flights** tab. Notification kind, reminder age, and cached detail availability add no visibility rules. This lookup makes no availability API or pre-open validation request. Opening a flight uses the normal detail loader, including its existing offline saved-detail requirements. The server queues assignment/invitation alerts, one schedule-update alert per employee for multi-flight scheduling, and 12-hour/2-hour/30-minute reminders before STA. Recipient and reminder eligibility follow the [Operations foundation](../../../docs/modules/operations-foundation.md#user-notifications). Notification transport and device registration are separate from flight reads. Device alerts reuse the inbox’s kind icon and color through Android’s standard notification layout, including matching colored large artwork; the system controls status-bar rendering. The single feed shows **New** first, then older notifications grouped by local date. Each kind has a distinct colored icon (assignment Scheduled blue, reminder orange, schedule info blue, invitation green). Live ages (`1s`, `5m`, `2h`, `3d`, `1w`, `1mo`) appear bold at the end of the message, advancing while the screen is open. The short rectangular action is labelled **View**. Date headings use balanced vertical spacing, and the notifications toolbar matches the main header height. Tapping the card does not navigate. A partial left swipe reveals the same compact red **Delete** control as the flight work forms; continuing to a full swipe deletes without an extra tap. Both use the existing archive operation, restore the row after a failed request, and animate successful removal. Screen readers expose the same action. Opening the inbox automatically acknowledges notifications through the newest loaded server creation timestamp, across all kinds; later alerts remain unread until observed. New items retain a subtle blue background tint for the current visit, including subsequently loaded pages, and become old on the next visit. There are no category tabs, manual read controls, or All/Unread filters. The virtualized list fetches older pages near the end of scrolling, with retry on a page error. Cached history remains available offline. Read state and the bell count are saved locally before a durable whole-inbox acknowledgement is attempted; pending reads retry on reconnect, foreground, or refresh, independently of screen navigation. Archive/delete actions continue to require the API.

Notifications use Room `NotificationsDatabase` version 3 in `operations-baseline.db`. The explicit 1 → 2 migration preserves existing notification rows and adds read-scope watermarks/pending acknowledgements and the last known whole-inbox unread count. The additive 2 → 3 migration preserves those records and adds optional per-category counts; older servers fall back to known cached unread rows. Previously fetched older pages are retained across first-page refreshes; temporary connection failures use the saved history. The previous `operations.db` and its dormant drafts/queued work remain unopened. Startup cancels the old WorkManager chain `operations-work-order-outbox` and tag `operations-outbox`; the retained legacy worker entry point performs no upload. This baseline does not replay or convert the old queue.

A failed or conflicting saved cancellation exposes **Review cancellation** in the flight sheet. It reopens the retained input; explicitly reload and review before saving again. **Revert cancellation** remains available to withdraw that intent.

Do not apply the separate `kotlin-android` plugin. APK naming uses the public `androidComponents` API. The app compiles and targets Android 17 (API 37), with minimum API 26 retained. See the [AGP compatibility requirements](https://developer.android.com/build/releases/agp-9-5-0-release-notes) and [built-in Kotlin migration](https://developer.android.com/build/migrate-to-built-in-kotlin).

The HTTP/realtime libraries use Ktor 3.6.1, kotlinx.serialization 1.12.0, kotlinx.coroutines 1.11.0, and SignalR 10.0.14. Existing Room schemas and explicit migrations remain unchanged. Validate Android 16/17 back navigation, edge-to-edge insets, large-screen resizing, and notification navigation on representative devices before release; a successful build or lint run alone does not establish runtime compatibility. The API URL is selected at build time through `BuildConfig.API_BASE_URL`.

For the current branch's Docker API, set the ignored `local.properties` entry:

```properties
operations.api.debug.base.url=http://10.0.2.2:5213
```

`10.0.2.2` is the Android emulator's host-loopback alias. Changing the property requires rebuilding the app.

### Run on a USB-connected phone

Keep the branch's Docker API running and reachable on the computer at `http://127.0.0.1:5213`. Enable USB debugging on the phone, connect it, and accept its USB debugging authorization prompt. For this workflow, replace the ignored `local.properties` API entry with:

```properties
operations.api.debug.base.url=http://127.0.0.1:5213
```

From this directory, list devices and replace `YOUR_PHONE_SERIAL` with the phone's serial below. `adb` must be on `PATH` (on this Mac it is in `~/Library/Android/sdk/platform-tools`). Selecting the serial avoids deploying to an emulator that is also running.

```sh
adb devices -l
phone_serial=YOUR_PHONE_SERIAL
adb -s "$phone_serial" reverse tcp:5213 tcp:5213
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
ANDROID_SERIAL="$phone_serial" ./gradlew :app:installDebug
```

The install task rebuilds the app with the configured URL. Open **Operations Module** on the phone, or select the connected Huawei phone in Android Studio and run **app** after syncing. [ADB reverse port forwarding](https://developer.android.com/develop/ui/views/layout/webapps/access-local-server) sends the phone's loopback port to the computer's API; repeat the reverse command after reconnecting the phone. To return to the emulator workflow, restore `operations.api.debug.base.url=http://10.0.2.2:5213` in `local.properties` and rebuild.

For a LAN connection instead of USB forwarding, use a reachable private IP or `.local` hostname for the same branch API. On Android 17, a configured private IP or `.local` backend prompts once for Nearby devices (local-network access). If denied, cached reads remain available; enable the permission in app Settings to reconnect. Public hosted API endpoints do not prompt. Other DNS names resolving to LAN addresses are not detected by this startup prompt.

Run debug checks from this directory, explicitly selecting that endpoint when desired:

```sh
export JAVA_HOME=$(/usr/libexec/java_home -v 17)
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug \
  -Poperations.api.debug.base.url=http://10.0.2.2:5213
```

These are verification commands, not a claim that a particular device journey has been observed. Report build/unit/lint results separately from emulator checks.

## Release configuration

Release does not read `local.properties`. Supply a compatible baseline backend URL with Gradle property `operations.api.release.base.url` or environment variable `OPERATIONS_API_RELEASE_BASE_URL`. The build validates an absolute HTTP/HTTPS URL, rejects emulator/loopback hosts and embedded credentials, and rejects queries/fragments.

Provision the ignored Android Firebase client file `app/google-services.json` for application ID `com.nags.operations` before release builds. Debug/unit builds can run without it; device registration then remains disabled. Every release build validates this file. It is distinct from the backend Firebase Admin credential.

For distribution, provide all four signing values through CI/environment variables or user-level Gradle properties:

| Gradle property | Environment variable |
|---|---|
| `operations.android.signing.store.file` | `OPERATIONS_ANDROID_SIGNING_STORE_FILE` |
| `operations.android.signing.store.password` | `OPERATIONS_ANDROID_SIGNING_STORE_PASSWORD` |
| `operations.android.signing.key.alias` | `OPERATIONS_ANDROID_SIGNING_KEY_ALIAS` |
| `operations.android.signing.key.password` | `OPERATIONS_ANDROID_SIGNING_KEY_PASSWORD` |

`assembleRelease` can produce an unsigned verification APK; `bundleRelease` requires the complete signing configuration. Application backup/device transfer remains disabled, with auth state, databases, and legacy outbox files excluded by the existing backup rules.
